# 买家测试方案

日期：2026-11-03。状态：方案，尚未实施；文中“现状”均按当日代码核对，引用位置以 `文件:行号` 标注。

本文取代《测试用例表-下单业务.md》前四节的测试计划部分；该表第五节的历史执行记录保留不动。

## 一、目标与范围

测试只回答一个问题：买家能不能顺利、安全地买到东西，出了问题能不能自己恢复，并且不丢钱、不丢货、不丢数据。

**买家主线**：游客浏览和搜索 → 选规格、看价格库存 → 加购或立即购买 → 登录（需要时） → 填写或选择地址 → 确认价格并提交订单 → 本人或亲友付款 → 查看订单 → 取消（待付款或待发货）/ 确认收货 / 评价。

| 纳入 | 不纳入本轮 |
| --- | --- |
| 上述主线；亲友代付（属于支付链路） | 游客整篮购物车及登录合并（下一阶段，见第十三节） |
| 待付款取消；已付款、待发货的取消并退款 | 发货后的拒收、退货、售后 |
| 支付确认中、超时宽限、重复和乱序回调 | 下单后改地址、物流拦截 |
| 亲友代收：只做后端和接口测试 | 商家端功能（只作为测试准备手段，例如替商家发货） |
| ArkWeb 收银台与 App 之间的往返 | Vue H5 页面：目前只有个人资料页（`shoph5-vue3/src/router/index.ts:5`），不属于购买链路 |

## 二、已定产品口径

| 编号 | 主题 | 口径 |
| --- | --- | --- |
| K1 | 游客加购 | 游客可以浏览、搜索、选规格。点“加入购物车”或“立即购买”时要求登录，登录成功后**自动完成那一次操作**，不用再点；这次操作带请求号，重试只生效一次。登录期间规格售罄或价格变化时，提示后让用户重选 |
| K2 | 亲友代付 | 属于支付链路，超时、结果未知、重复回调都要覆盖；真机冒烟包含一条代付链路 |
| K3 | 付款时限 | 订单从创建起 15 分钟内未发起支付，自动取消并释放库存。15 分钟内发起支付的，订单进入“支付确认中”，从发起支付起额外宽限 10 分钟 |
| K4 | 支付结果未知 | 显示“支付确认中”，可以手动刷新；查到结果前不能再次付款，也不释放库存。宽限期满先向支付渠道查单，再决定成功、取消或退款 |
| K5 | 宽限期后才确认的付款 | 订单保持取消，自动原路退款，并通知用户 |
| K6 | 价格变化 | 提交前价格变了，页面自动换成新价格让用户看到，用户再点一次才下单；确认新价格后使用新的请求号 |
| K7 | 库存不足 | 结算页加载时就标出库存不足的商品；提交时才发现不足的（例如多人抢最后一件），整单不提交，并突出显示是哪件商品 |
| K8 | 登录过期或换账号 | 重新登录同一账号：回到结算页，商品、地址和价格确认保留。换成另一账号：回到首页，不带上一个账号的任何数据，也不执行上一个账号未完成的操作 |
| K9 | 已付款取消 | 已付款、待发货的订单可以取消并退款。只有下单人能发起；代付订单退回付款人原来那笔支付。取消与商家发货同时发生时，先成功的一方为准，另一方收到明确提示。退款失败显示“退款处理中”，可以重试，不会重复退款 |
| K10 | 发货后取消 | 不能取消，转售后处理；售后本轮不做 |
| K11 | 立即购买与加购分开 | 两条路径互不影响。“立即购买”只结算当前这件商品和所选数量，不读也不改购物车；下单成功后，购物车里原有的同款保留。“加入购物车”成功后直接跳到购物车页，让用户看到之前加过的其他商品，再从购物车结算 |

## 三、订单状态

订单履约状态和支付退款状态分开记录。现有订单状态只有一条线（`orders.ts:9`），支付直接把订单改为待发货（`orders.ts:313`），没有支付记录和退款记录。

**履约状态**：待付款 → 待发货 → 待收货 → 待评价 → 已完成；任何时候都可能进入“已取消”。

**支付状态（每笔支付一条记录）**：确认中 → 成功 / 失败 / 已关闭。
**退款状态（每笔退款一条记录）**：退款中 → 已退款 / 退款失败（可重试）。

| 起点 | 事件 | 结果 | 库存 |
| --- | --- | --- | --- |
| 待付款 | 15 分钟内发起支付 | 待付款 + 支付确认中，宽限至发起后 10 分钟 | 继续占用 |
| 待付款 | 15 分钟到，未发起支付 | 已取消 | 释放一次 |
| 支付确认中 | 宽限期内回调或查单为成功 | 待发货 | 不变 |
| 支付确认中 | 回调或查单为失败 | 待付款（未超 15 分钟，可再付）或已取消 | 取消时释放一次 |
| 支付确认中 | 宽限期满 | 先查单：成功按上行处理；明确未付则取消；仍未知则保持确认中并继续查单 | 查到确定结果前不释放 |
| 已取消 | 迟到的成功回调 | 保持已取消，创建退款 | 不变 |
| 待发货 | 下单人取消 | 已取消 + 退款中，同时阻止发货 | 释放一次 |
| 待发货 | 商家发货先成功 | 待收货；之后的取消请求收到“已发货，请联系售后” | 不变 |
| 退款中 | 退款失败 | 退款失败，可重试；重试沿用同一退款单 | 不变 |
| 任意 | 重复、乱序或伪造的回调 | 状态只前进一次；伪造回调被拒绝；乱序到达的旧回调不能覆盖新结果 | 不变 |

## 六、隔离规则

1. 每条测试自己创建账号、商品、库存、地址和订单，不读取其他测试或种子数据的结果。
2. 数据库按测试（L1 到 L3）或按运行（L4）新建，用完即丢；不依赖结束时逐条清理，测试中途崩溃也不会留下数据。
3. 时间一律用可控时钟；断言不依赖真实等待。
4. 测试顺序随机打乱也必须通过；CI 定期以随机顺序运行一次。
5. 只替换外部依赖：支付渠道、短信、地图、相机、语音。数据库、库存、订单和金额计算用真实代码。
6. 每个模拟器至少提供成功、失败、超时和重复四种结果；支付模拟器另加乱序、伪造和迟到回调。

## 八、真机冒烟

真机只验证单元测试测不到的部分：页面衔接、权限、键盘、返回、网络切换、ArkWeb 收银台往返和最终可用性。每次运行使用独立夹具，所有前置数据由夹具准备，页面上只做买家操作。

| 链路 | 步骤 | 覆盖用例 |
| --- | --- | --- |
| S1 本人完整购物 | 游客搜索 → 详情选规格 → 加购触发登录 → 自动加购并跳到购物车 → 购物车结算 → 新建地址 → 提交 → 收银台付款 → 订单待发货 → 夹具替商家发货 → 确认收货 → 评价 | B-01、B-10、B-22、B-30、B-40、B-49、B-66 |
| S2 亲友代付 | 已登录买家（购物车里预先放有其他已勾选商品）立即购买 → 结算页只有这件商品 → 提交 → 指定亲友代付 → 切换到亲友账号付款 → 切回买家看到已付款，购物车不变 | B-17、B-50、B-70 |
| S3 恢复与取消 | 提交后在收银台取消 → 杀进程重进 → 从订单继续付款 → 付款后取消待发货订单 → 看到退款 | B-33、B-41、B-49、B-62 |

S1 每次提交都跑，S2、S3 每日或发版前跑。网络切换在 S1 的提交和付款步骤各断网一次。

## 九、结果记录

自动化回归和真人可用性测试分开记录，指标不能混用。

**自动化回归**（每次运行）：通过、失败、跳过数；失败用例卡在哪一步；对应截图、页面布局和接口日志；同一用例连续三次结果不一致即标记为不稳定，修复前不计入通过。

**可用性测试**（每个版本找 3 到 5 人，用于发现问题，不作为通过标准）：按任务记录，例如“买一双袜子并让亲友代付”“付款后取消订单”。

| 指标 | 记录方式 |
| --- | --- |
| 任务完成 | 独立完成 / 提示后完成 / 未完成 |
| 卡住位置 | 页面和操作 |
| 误操作次数 | 点错、返回、重复提交 |
| 恢复路径 | 用户是怎么自己走出来的，或为什么走不出来 |
| 是否需要解释 | 需要人工说明的文案或状态 |

## 十、审查清单

每次新增或修改测试，按以下问题审查：

1. 这条测试对应哪个买家任务？和买家无关的不进入本套测试。
2. 是否自己准备全部数据？打乱顺序、单独运行是否都能通过？
3. 是否只替换了外部依赖？模拟器是否会让真实问题被掩盖（例如模拟支付永远同步成功）？
4. 异常场景之后，用户能否自己恢复？恢复后是否不丢钱、不丢货、不丢数据？
5. 断言是否同时写了用户看到的结果和系统记录？
6. 真机冒烟是否仍然覆盖 S1 的每一步？
