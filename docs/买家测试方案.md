## 一、目标与范围

测试只回答一个问题：买家能不能顺利、安全地买到东西，出了问题能不能自己恢复，并且不丢钱、不丢货、不丢数据。

**买家主线**：游客浏览和搜索 → 选规格、看价格库存 → 加购或立即购买 → 登录（需要时） → 填写或选择地址 → 确认价格并提交订单 → 本人或亲友付款 → 查看订单 → 取消（待付款或待发货）/ 确认收货 / 评价。

| 纳入 | 不纳入本轮 |
| --- | --- |
| 上述主线；亲友代付（属于支付链路） | 游客整篮购物车及登录合并（下一阶段，见第十三节） |
| 待付款取消；已付款、待发货的取消并退款 | 发货后的拒收、退货、售后 |
| 支付确认中、超时宽限、重复和乱序回调 | 下单后改地址、物流拦截 |
| 亲友代收：只做后端和接口测试 | 商家端功能（只作为测试准备手段，例如替商家发货） |
| 应用内收银页（`PayView`）与订单页之间的往返 | 真实支付渠道：现在付款是应用内演示页，“不产生真实扣款”（`PayView.ets:375`）；接入渠道后另加渠道链路 |
| | Vue H5 页面：目前只有个人资料页（`shoph5-vue3/src/router/index.ts:5`），不属于购买链路 |

## 二、已定产品口径

| 编号 | 主题 | 口径 |
| --- | --- | --- |
| K1 | 游客加购 | 游客可以浏览、搜索、选规格。点“加入购物车”或“立即购买”时要求登录，登录成功后**自动完成那一次操作**，不用再点；这次操作带请求号，重试只生效一次。登录期间规格售罄或价格变化时，提示后让用户重选 |
| K2 | 亲友代付 | 属于支付链路，超时、结果未知、重复回调都要覆盖；真机冒烟包含一条代付链路 |
| K3 | 付款时限 | 订单从创建起 15 分钟内未发起支付，自动取消并释放库存。15 分钟内发起支付的，订单进入“支付确认中”，从发起支付起额外宽限 10 分钟 |
| K4 | 支付结果未知 | 显示“支付确认中”，可以手动刷新；查到结果前不能再次付款，也不释放库存（用户主动取消除外，见 K12）。宽限期满先向支付渠道查单，再决定成功、取消或退款 |
| K5 | 宽限期后才确认的付款 | 订单保持取消，自动原路退款，并通知用户 |
| K6 | 价格变化 | 提交前价格变了，页面自动换成新价格让用户看到，用户再点一次才下单；确认新价格后使用新的请求号 |
| K7 | 库存不足 | 结算页加载时就标出库存不足的商品；提交时才发现不足的（例如多人抢最后一件），整单不提交，并突出显示是哪件商品 |
| K8 | 登录过期或换账号 | 重新登录同一账号：回到结算页，商品、地址和价格确认保留。换成另一账号：回到首页，不带上一个账号的任何数据，也不执行上一个账号未完成的操作 |
| K9 | 已付款取消申请（2026-11-06 修订） | 仅下单人可对已付款待发货订单申请取消，弹窗写明金额与原路去向，代付退实际付款亲友；审核中商家不能直接发货。处理前可撤回，不限撤回再申请次数，同单最多一个pending，每次新申请重新计72小时。商家同意后已取消、释放一次库存、原有效支付退款；拒绝须填原因并同时发货，买家看原因及“如有问题请联系客服”，发货后不再取消。72小时硬截止自动同意，晚到撤回/处理不能抢先生效；同事务裁决，不既发货又取消有效支付退款，重试/24小时转人工沿用第二步 |
| K10 | 发货后取消 | 不能取消，转售后处理；售后本轮不做 |
| K11 | 立即购买与加购分开 | 两条路径互不影响。“立即购买”只结算当前这件商品和所选数量，不读也不改购物车；下单成功后，购物车里原有的同款保留。“加入购物车”成功后直接跳到购物车页，让用户看到之前加过的其他商品，再从购物车结算 |
| K12 | 支付确认中取消 | 下单人可以取消。订单立即变为已取消，关闭支付单，释放库存，并提示“如已扣款，将原路退回”；之后这笔支付若确认成功，自动退款。亲友不能取消代付订单 |
| K13 | 回调与查单结果相反 | 以查单为准。连续两次查单仍与回调相反，保持“支付确认中”，转人工核实 |
| K14 | 结果一直未知 | 持续查单，最长 24 小时，期间库存保留、订单显示“支付确认中”。24 小时后转人工核实，并通知买家“我们正在核实这笔付款”；库存等人工核实后再处理。买家仍可按 K12 主动取消 |

## 三、订单状态

2026-11-06 修订：履约、支付、退款和取消申请分开记录，支付退款沿用第二步；审核中是待发货子状态，不新增履约数字。申请/撤回不退款不释放，同意/超时同意后才已取消，拒绝必须同时发货。

**履约状态**：待付款 → 待发货 → 待收货 → 待评价 → 已完成。待付款按原规则直接取消；已付款待发货须申请并获商家同意或72小时自动同意后取消，拒绝则同时发货；待收货及之后不能取消（K10）。（2026-11-06 修订）

**支付状态（每笔支付一条支付单）**：确认中 → 成功 / 失败 / 已关闭。
**退款状态（每笔退款一条退款单）**：退款中 → 已退款 / 退款失败（可重试）。

回调和查单都以支付单为准做幂等：同一支付单的结果只处理一次。退款以退款单为准：重试沿用同一退款单，同一笔支付最多退一次。

### 时间点

| 记号 | 含义 | 规则 |
| --- | --- | --- |
| T0 | 创建订单 | 付款时限 = T0 + 15 分钟 |
| T1 | 发起支付（创建支付单） | 必须**早于**付款时限，刚好到点不能再发起；宽限截止 = T1 + 10 分钟，到点关闭支付单 |
| T2 | 渠道实际扣款时间 | 只采信渠道给出的交易成功时间，来源是验签通过的回调或查单结果；本地收到消息的时间不算 |
| T3 | 回调到达时间 | 只是通知手段，不决定结果 |
| T4 | 查单时间 | 宽限截止时必查一次；仍未知则继续定时查 |

判定规则：

1. **T2 不晚于宽限截止（含刚好等于），付款成功；晚于宽限截止，自动退款（K5）。** 回调到达得晚（T3 晚于截止），但 T2 在截止前的，仍算付款成功，因为在查到结果前库存一直保留（K4）。
2. 渠道结果缺少交易时间，或回调与查单相反时，不按先到的结果处理：保持“支付确认中”并保留库存，按 K13、K14 继续查单或转人工。
3. 付款失败发生在付款时限内，回到待付款，可以再付；发生在付款时限之后，订单直接取消，不能再付款。
4. 同一订单有多笔支付成功时，保留**最先被系统确认成功**的一笔为有效支付，之后确认成功的各笔自动退款；有效支付一旦确定不再更换，避免页面显示付款成功后又改换付款人。订单已取消的，全部退款。多笔结果同时到达时，在同一事务里裁决。（2026-11-05 修订，原为“保留 T2 最早的一笔”）

| 起点 | 事件 | 结果 | 库存 |
| --- | --- | --- | --- |
| 待付款 | 付款时限内发起支付 | 待付款 + 支付确认中，宽限至 T1 + 10 分钟 | 继续占用 |
| 待付款 | 付款时限到，未发起支付 | 已取消 | 释放一次 |
| 支付确认中 | 回调或查单为成功，且 T2 不晚于宽限截止 | 待发货 | 不变 |
| 支付确认中 | 回调或查单为失败 | 未过付款时限：回到待付款，可以再付；已过付款时限：已取消 | 取消时释放一次 |
| 支付确认中 | 宽限截止 | 关闭支付单并查单：成功按上面处理；明确未付则取消；仍未知则保持确认中并继续查单（K14） | 查到确定结果前不释放 |
| 支付确认中 | 关闭支付单的同时用户正在付款 | 以渠道结果为准：渠道关单成功则这笔不会再成功；渠道返回已扣款则按判定规则 1 处理 | 按结果处理 |
| 支付确认中 | 回调与查单结果相反，或缺少交易时间 | 保持确认中；连续两次查单仍相反转人工（K13） | 不释放 |
| 支付确认中 | 下单人取消（K12） | 已取消，关闭支付单；之后若确认成功则自动退款 | 释放一次 |
| 支付确认中 | 取消与支付成功同时到达（2026-11-06 修订） | 取消先落库立即取消，迟到成功退款；成功先落库拒绝旧取消，刷新后重新确认取消申请，不承诺两顺序都立即退款 | 真正取消时释放一次 |
| 已取消 | 迟到的成功结果（T2 晚于宽限截止、订单已因失败取消后又收到成功，或用户在确认中取消后才确认成功） | 保持已取消，创建退款单 | 不变 |
| 已取消 | 迟到的失败结果 | 忽略，订单不变 | 不变 |
| 待发货 | 同一订单另一笔支付也成功（例如第一笔判定失败后用户重付，第一笔又迟到成功） | 保留最先被确认成功的一笔为有效支付，之后确认的自动退款；退款失败按普通退款重试 | 不变 |
| 待发货 | 下单人申请取消（2026-11-06 修订） | 待发货+取消申请审核中；商家普通发货被拒，必须处理申请 | 继续占用，不退款 |
| 待发货 | 商家普通发货先成功（2026-11-06 修订） | 仅无pending时可发货；之后申请提示“已发货，请联系售后” | 不变 |
| 待发货+审核中 | 下单人撤回，未到72小时（2026-11-06 修订） | withdrawn，仍待发货，可再申请，不计次 | 不变 |
| 待发货+审核中 | 商家同意（2026-11-06 修订） | 已取消+退款中，退款原因cancelled，以申请refund_id区分来源，禁止发货 | 释放一次 |
| 待发货+审核中 | 填原因拒绝并发货（2026-11-06 修订） | 待收货，显示原因和客服文案，不可再取消 | 不变 |
| 待发货+审核中 | 72小时到点（2026-11-06 修订） | 系统自动同意；迟到处理/撤回先落实自动同意再返回冲突 | 释放一次 |
| 待发货+已撤回 | 再次明确申请（2026-11-06 修订） | 新申请、新72小时截止；旧申请不复活 | 不变 |
| 退款中 | 退款失败 | 退款失败，可重试；重试沿用同一退款单 | 不变 |
| 任意 | 重复、乱序或伪造的回调 | 状态只前进一次；伪造回调被拒绝；乱序到达的旧回调不能覆盖新结果 | 不变 |

| L4 真机冒烟 | 页面衔接、权限、键盘、返回、网络切换、杀进程重进、收银页与订单页往返、最终可用性 | `scripts/device-trade-regression.ps1` | 每次运行一个独立内存库夹具，所有数据由夹具通过接口准备 |

**执行位置与通过门槛**：

- L1 至 L3 只依赖 Node，每次推送和合并请求都在 CI 上运行，必须全部通过才能合并。现在的 CI 只检查 H5（`.github/workflows/ci.yml:9`），不跑 `server/test` 和 `scripts/tests`，要先补上。
- L4 依赖本机 DevEco 环境、签名和设备，CI 托管机没有这些环境（`.github/workflows/ci.yml:42`）。L4 在本机运行，S1 在提交前、S2 和 S3 在每日或发版前必须通过，结果和截图按第九节归档。

L4 在模拟支付下运行，只能证明页面链路走得通，不能证明真实支付渠道的行为。结果未知、迟到、重复和伪造回调等支付行为，由 L1 至 L3 用支付模拟器验证。

`hdm_uitest/` 使用共享账号 `test_a`、`test_b` 和固定商品（`hdm_uitest/config.py:9`），每条用例结束只回到首页（`base_case.py:37`），其中关于 ArkWeb 收银台的说明也已过时。它的用例按第七节逐条迁到 L3 或 L4 后停用，迁移完成前不作为通过依据。

## 六、隔离规则

1. 每条测试自己创建账号、商品、库存、地址和订单，不读取其他测试或种子数据的结果。
2. 数据库按测试（L1 到 L3）或按运行（L4）新建，用完即丢；不依赖结束时逐条清理，测试中途崩溃也不会留下数据。
3. 时间一律用可控时钟；断言不依赖真实等待。
4. 测试顺序随机打乱也必须通过；CI 定期以随机顺序运行一次。
5. 只替换外部依赖：支付渠道、短信、地图、相机、语音。数据库、库存、订单和金额计算用真实代码。
6. 每个模拟器至少提供成功、失败、超时和重复四种结果；支付模拟器另加乱序、伪造和迟到回调。
7. L3、L4 使用关闭演示订单开关的构建（`GlobalVariable.ets:24` 的 `DEMO_ORDER_FLOW`）。打开时，不经过后端的订单会在本机直接推进状态（`PayView.ets:245`），会掩盖后端的真实结果。

## 八、真机冒烟

真机只验证单元测试测不到的部分：页面衔接、权限、键盘、返回、网络切换、杀进程重进、收银页与订单页往返和最终可用性。每次运行使用独立夹具，所有前置数据由夹具准备，页面上只做买家操作。

以下链路都在模拟支付下运行，是**模拟支付下的页面链路**，证明页面走得通，不证明真实支付渠道。取消与发货并发、退款失败重试、伪造回调等在真机上无法稳定复现，留在 L1、L2。

| 链路 | 步骤 | 覆盖用例 |
| --- | --- | --- |

### 接口及错误格式

- POST /member/order 必填 requestKey、addressId、goods 和 expectedAmountCents（正整数分）；示例：{ requestKey: '至少16字符请求号', addressId: '地址id', goods: [{ skuId: '规格id', count: 3 }], expectedAmountCents: 30 }。成功保持 { code: '1', result: { id: '订单id' } }。
- 报价变化：HTTP 409，{ code: '0', msg, requestId, reason: 'PRICE_CHANGED', result: { totalAmountCents: 33, goods: [{ skuId, name, spec, priceCents: 11, count: 3, subtotalCents: 33 }] } }。整单无订单、无扣库存、无删购物车。
- 库存不足：HTTP 409，{ code: '0', msg, requestId, reason: 'STOCK_SHORTAGE', result: { goods: [{ skuId, name, spec, requiredCount: 3, remainingCount: 1 }] } }。包含所有不足规格，事务保证整单不提交。
- GET /member/order/by-request/:requestKey 仅按当前账号和请求号查询；成功 { code: '1', result: { id, orderState, expiresAt } }，不存在或属于他人均为 404。不会创建订单，不标记订单提醒已读；沿用订单查询既有的到期检查，已超时返回取消状态。
- 普通错误仍为 { code: '0', msg, requestId }，仅结构化冲突扩展 reason/result；客户端兼容 Axios 的 response.status/data，不改变已有网络调用方。

### 请求号、存储和页面规则

- StoreManager 按稳定账号 id 保存 pendingOrder:账号id 的 JSON（accountId、requestKey、summary），summary 记录地址、按规格排序的商品数量及整数分报价，不依赖购物车入口，也不保存令牌；等待 flush 完成后才发创建请求，存储失败不发送。
- 同次提交只允许一个创建请求；商品、地址或报价变化后生成新请求号。结果未知时显示“正在确认订单”，按钮“重新确认订单”仅 GET 旧号，不重放 POST；404 才清记录并允许新提交。408、429、5xx、断网均按未知处理；明确的其他 4xx 清记录。
- 价格冲突只更新单价、小计和总额，关闭旧支付确认层并保持可提交；用户再次点击才创建。库存不足显示具体名称、规格及剩余数量，禁用提交，调整入口明确打开购物车。
- 首页在启动、登录账号更新、回到前台时尝试恢复；网络故障静默保留，下一次启动或前台恢复时再查，不加后台轮询依赖。待付款只弹一次带“去付款”的对话框，不自动跳转；不是待付款则静默清除；404 提示一次“上次提交没有成功，商品仍在购物车里”。
- 付款提示采用固定但限定起点的“上次提交的订单已生成，请在订单创建后15分钟内付款”，避免误解为从重进时再给15分钟；收银页沿用真实剩余时间。
- pageGeneration、token、sequence 和账号 id 共同隔离迟到响应；弹窗返回后再次核对会话再导航。其他账号记录不查询、不提示、不清除。演示模式不启用请求落盘和恢复，不改变演示支付流程。
- 购物车合计与结算行小计先转换为整数分再乘数量、累加，仅展示时转元；订单和支付继续使用整数分。
