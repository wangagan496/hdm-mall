# 商家库存调整验收

日期：2026-10-28；范围为现有规格的可售库存增减、原生商家入口、调整流水、重试保护及版本 4 迁移。

本文保留库存调整阶段的版本 4 和 115 项测试历史证据；当前版本 5 增加头像路径迁移，库存规则不变，2026-10-29 库存页面隔离补充后的服务端与客户端共 252 项检查通过，见本文末尾及《优化记录.md》。

## 已实现行为

商家登录后从「我的 → 库存管理」进入，分页查看库存，选择规格、增加或减少、数量及原因，核对确认框后提交；普通买家没有入口，服务端仍独立校验商家身份。原因须为去除首尾空白后的 5～200 字，单次调整绝对值为 1～1000000，最终可售库存为 0～2147483647。

提交同时携带页面读取的 expectedStock；库存已被下单或其他调整改变时返回 409，要求刷新后重新确认。库存与流水合计不一致时拒绝调整，不能用人工增减掩盖已有差异。库存更新与带操作人、原因、数量、余额、时间及业务编号的 adjust 流水在同一事务内提交，任一步失败全部回滚，历史流水不可修改或删除。

同一商家、同一 requestKey、同一份内容重复提交只返回原凭据，不再次增减库存；同编号更改内容返回 409，其他商家不能查询该编号对应的私人提交凭据。当前项目为自营商城，商家角色管理共同商品库存，不是多租户商品所有权体系。

原生端在发请求前按账号持久保存固定请求快照；连续点击复用同一请求，回应丢失后查询原凭据，结果未知则保留快照。重新进入页面可点击「查询并重试本次调整」，先查询，确认尚未记录后才用原编号和原内容重试；上一笔未确认时不能另开新调整。换账号后迟到结果不回写当前页面；确认后清理本地记录失败仍保留原请求，避免生成新编号重复加库存。

调整成功后刷新列表；列表刷新失败会保留「调整已记录」及本次余额，另提示刷新失败。列表使用包含行内容的标识，避免接口替换普通对象后复用旧显示或旧编辑基准；固定浅色卡片的文字显式使用深色，避免跟随系统深色文字主题后不可见。

## 接口与迁移

| 方法与路径 | 内容 |
| --- | --- |
| PUT /merchant/inventory/:id/adjustments | id 为规格编号；提交 requestKey（UUID）、delta、expectedStock、reason，返回 id、skuId、delta、balance、reason、createdAt |
| GET /merchant/inventory/adjustments/:id | id 为 requestKey；只查询当前商家自己的原调整凭据，未找到返回 404 |
| GET /merchant/inventory | 分页读取实际库存、流水合计与差额 |
| GET /merchant/inventory/:id/movements | 分页读取规格流水，现包含 reason 字段 |

server/src/migrations/004-stock-adjustment.sql 在事务内重建流水表，保留旧记录编号、索引及不可修改约束，新增 adjust 与 reason；迁移中途失败时原表、数据和版本号均回滚。数据库版本为 4，备份工具接受版本 2、3、4；旧备份恢复到新目录后由当前程序升级，禁止把新库直接交给不支持该版本的旧程序打开。

## 2026-10-29 库存页面隔离补充

`InventoryView.ets` 的首次加载、刷新及读取失败状态不能提交新调整；保留原列表和编辑输入供查看，成功重新读取后才恢复操作。换账号或角色清空旧列表、表单与提示，仅昵称等资料变化保留编辑且不重读。隐藏页面不发起查询或提交，返回及可见页面回到前台重新读取；旧查询、旧提交成功失败及收尾不能影响同账号重进后的新操作。

确认框固定页面、会话、查询及弹窗编号；刷新、离页、换账号、换角色、取消及新弹窗使旧回调失效。确认时再次核对当前规格、可售库存、流水差额、数量、方向和原因，已使用的确认回调不能重复提交。页面向 `InventoryAdjustment.start` 与 `resume` 显式传递发起凭证，存储层已切换账号但页面尚未更新时直接拒绝，不能借新账号提交旧表单。

调整失败使在途旧查询失效，新调整必须刷新后才能继续；已有待确认快照仍可使用原编号查询恢复，不要求先成功读取列表。损坏的本地待办有独立错误提示并拦截新调整；成功写入后刷新失败保留已记录提示，单独展示列表刷新错误。服务端角色权限、库存基准校验、持久化草稿及原编号幂等恢复规则保持不变。
