# 惠多美故障导演台：链路追踪工具选型

查询日期：2026-11-16（Asia/Shanghai）。状态：只读调研完成，待独立审核。

## 1. 先看演示能得到什么

因：面试官想看到“刚才这一下点击，为什么慢了、有没有拖垮主业务、你怎么找到原因”，不需要先看十个监控产品的首页。

果：首推“OpenTelemetry（OTel）+ Jaeger 2 + rrweb + Node 手写故障开关”，前面加一个精简 OTel Collector；导演台由项目自己的 React 页面组织，一边显示操作回放，一边跳到同一条 trace 的瀑布图，再给出有证据的排障说明。Jaeger 能单进程收集、查询并自带界面；rrweb 提供网页录制与回放基础库；Collector 统一接收、处理、导出遥测数据。[S01][S04][S07][S20]（查询：2026-11-16）

行：先让 Node 与两个网页端用标准 OTel，鸿蒙原生端手工生成并传递 W3C traceparent，同时记录最小客户端 span；数据库在现有封装里手工打点。HiTraceChain 作为设备内排障的另一条线，用关联字段对照，暂不承诺能无损转换成 OTel。这里是选型建议与接入设计，尚未实际安装或验证。[S02][S05][H01][H02]（查询：2026-11-16）

最有价值的作品集表述是“我打通了跨运行时上下文、用可控故障验证降级，并能把一次操作还原为有因果关系的证据”；仅打开现成监控界面不能证明这些能力。这是本报告的评价判断。

## 2. 项目边界与兼容性

本次只读核对得到以下基线，查询日期均为 2026-11-16：

| 对象 | 当前证据 | 对选型的影响 |
|---|---|---|
| Node 后端 | server/package.json 声明 Node >=24、Fastify ^5.6.2；package-lock.json 实际锁定 Fastify 5.12.7 | 以 Fastify 5 与 Node 24 系列为接入目标，不能只按 package.json 的下界挑插件；未运行 Node，实际可执行文件版本未核实 |
| 数据库 | server/src/database.ts 使用 node:sqlite 的 DatabaseSync，单库 | 不是 sqlite3 或 better-sqlite3 包；那些包的自动探针不能直接当作 node:sqlite 支持证明 |
| Vue H5 | package.json 声明 Vue ^3.5.32、Vite ^8.0.8、axios ^1.17.0；src/api/index.ts 已有统一请求拦截器 | 适合在现有请求层传递上下文；不能假设原生 @ohos/axios 与浏览器 axios 共用探针 |
| HarmonyOS | mixed-development-h5/build-profile.json5 的兼容与目标版本均为 6.1.1(24)；commons/network 使用 @ohos/axios 2.2.4 | ArkTS 请求拦截器可成为手工 header 接入点；原生 SDK 不是 Node SDK，也不是浏览器 SDK |
| React 商家后台 | 本任务给定 React 19、计划新建；本次未找到实际后台依赖锁定证据 | React 19 的探针兼容性按官方包元数据和后续小验证确认，不能写成现有端已经接通 |

“三端”是三个请求发起端：原生 ArkTS、ArkWeb 中的 Vue H5、独立 React 网页；一次具体点击通常只经过其中一个发起端再到 Node 与数据库，并不天然经过三个客户端。原生打开 H5 后继续同一业务操作时，需要显式桥接上下文。上述是本项目架构推导。

所有产品的“本机资源轻/中/重”都是按组件数、数据库依赖和维护步骤做的相对判断，不是本机实测；本次没有启动 Docker、服务、构建、测试或设备。云服务免费档的配额和价格可能变化，本报告不编造可长期保证的免费额度。

以下兼容性分成两层：后端能收 OTLP/Zipkin 数据，不代表它为 React 19、Vite 8 或 ArkWeb 提供经过认证的客户端 SDK；实际浏览器能力、跨域、原生桥和 Node 加载顺序仍需验证。OTel 官方明确浏览器插桩仍是实验性，且没有官方浏览器支持名单，不能把 ArkWeb 的 Chromium 内核等同于已认证支持。[S01][S03]（查询：2026-11-16）

本节各行官方链接见编号对应来源，统一查询于 2026-11-16；“维护成本”和面试话题是针对本项目的判断。

Fastify 接入有一处容易踩坑：选官方 @fastify/otel，并按它的版本说明与测试矩阵固定依赖，而不是复制旧 @opentelemetry/instrumentation-fastify 教程。查询时官方仓库 main 的 package.json 显示 1.0.1、含 Fastify v4/v5 测试；README 要求 Node >=22.15、OTel API 1.10.x、SDK 3.x、实验包 0.300.x。这里是 main 分支快照，不证明这些版本已在本仓库安装或是未来实施时的最终可下载版本；实施前应选择实际发布 tag 与锁文件相配的组合，不混装 OTel 2.x 示例。该插件 MIT；本次旧 contrib README 路径返回 404，不能据此证明所有旧版都不存在或已弃用。[S06]（查询：2026-11-16）

数据库底线：Node 24 文档说明 DatabaseSync 及其语句 API 同步执行；本次未查到 OTel 官方针对 node:sqlite 的已验证自动插桩方案。建议在 database.ts 的读、写、事务封装外创建 span，记录语句类别、表名或稳定操作名、成功/失败与耗时，不上传 SQL 参数或用户明文；事务 span 包住语句子 span，手工 span 在 finally 中结束。这样会给出数据库调用耗时，但不自动提供 SQLite 内核级锁等待剖析。[S33]（查询：2026-11-16；接入方式为建议）

## 4. 追踪后端与界面

这些后端负责“保存与查阅请求走过哪里”，不会自动生成业务埋点，也不会自动替你写降级逻辑。下面的三端兼容均指第 3 节的采集与传播方案，不表示后端厂商为 ArkTS 发了 SDK。

| 候选：用途与观众界面 | 三端及版本适配 | 单机运行与资源判断 | 免费、开源与许可证 | 学生维护、采用证据、面试话题 |
|---|---|---|---|---|
| Jaeger：专注 trace；能按服务、操作、耗时查请求，展开父子 span 瀑布图 | Node/Fastify、Vue/React 通过 OTel 发 OTLP；ArkTS 通过手工 span 适配；不负责原生录屏，也不负责 node:sqlite 自动插桩 | 官方 Jaeger 2 all-in-one 是单进程，可用容器运行；默认内存存储重启就丢，保留演示历史应配置 Badger 或另选持久化；相对轻。查询时 latest 指向 2.23，实施时固定版本 | Apache-2.0，开源、自托管免费 | 低到中；官方 ADOPTERS 列有 Uber、Red Hat，是有来源的历史采用证据，不能证明截至今天的全公司覆盖率。可讲 trace 关键路径、存储生命周期、标准 OTLP 和查询 API。[S07] |
| Grafana Tempo：trace 存储与查询引擎，通常在 Grafana Explore 中看瀑布图，TraceQL 搜索满足条件的请求 | 同一套 OTel/OTLP 接入三端；React 19、Vue 3、Vite 8 兼容性由采集层决定；ArkWeb 未有认证证据 | 官方有 Docker Compose 开发示例；可单体部署，但常要再配 Grafana，持久化与对象存储规划比 Jaeger 默认演示多；相对中 | Tempo 为 AGPL-3.0；OSS 自托管免费，Grafana Cloud 是另一个收费/免费档产品 | 中；本次未查到足够具体的官方“大厂正在使用 Tempo”案例，不能用 Grafana 客户名单替代 Tempo 证据。可讲 TraceQL、trace/日志/指标互相跳转、为何大规模存储设计不等于学生项目必须照搬。[S08][S13] |

建议事件最小结构如下，这是导演台自建协议，不是工具自带功能：

```text
session_id / action_id / event_id / sequence
event_type / event_time / received_time / service_name
trace_id / span_id / replay_id / replay_offset_ms
business_action（稳定动作名）/ result（脱敏状态）
```

每个会话有单调递增序号，同一 action 可以关联多次重试的请求 span；跨设备时钟不能直接当因果顺序，展示客户端时间和接收时间，并以 parent/child、action 和序号辅助对齐。rrweb 事件压缩文件可放本机受控目录，元数据与语义事件先放现有单库的独立表；这不是要求把业务改成多数据库，也不承诺回放和数据库状态能无损还原。

### 8.2 ArkTS 如何把 traceparent 传给 Node

因：OTel 官方语言目录与本次华为官方搜索没有给出 ArkTS SDK，但 W3C 的上下文是普通请求头；不依赖原生 OTel SDK也能先把链路身份打通。[S01][S02][H06]（查询：2026-11-16）

果：Node 能把原生客户端操作当成父节点接着追踪；前提是客户端那个 span 也被采集存储，只有 header 并不会凭空在 Jaeger 生成原生点击这一行。

行：建议按以下顺序实现，均为待实施方案，不是本次已写入项目的代码。

1. 用户点“刷新推荐”时，新建 action 上下文；安全随机生成 16 字节 trace ID 与 8 字节 span ID，写成小写十六进制，检查非全零；同一 action 下每次 HTTP 请求生成自己的客户端 span ID，重试不得重复使用请求 span ID。W3C 样例格式为 `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`；末尾 01 是采样标志，不是业务权限。[S02]
2. 在 commons/network/src/main/ets/RequestAxios.ets 的请求拦截器放入当前请求的 traceparent；必要时带 tracestate。华为官方 HTTP API有 header 字段，本仓库的 @ohos/axios 拦截器也已有设置 header 的位置，但本次没有验证该库对 traceparent 的具体运行行为。trace 身份只发给自己允许的 Node 服务，不发给支付/物流等外部站点。[H05] 加本地源码证据
3. Node 的 OTel HTTP 入站提取 traceparent，创建新的 SERVER span，其 trace ID 与客户端相同，parent span ID 指向该次客户端请求 span；Fastify/业务/SQLite 手工 span 接在后面。不要把客户端 header 原封不动复用为所有下游请求，应由当前活动 span 注入新的上下文。[S05][S06]
4. 原生同时记录操作和请求的开始/结束、状态、父 ID、service.name，再批量发到自己的受控遥测适配端点；适配端验证后转为 OTLP span，保留客户端原有 trace/span ID、父子关系与时间，发给 Collector。若在服务端生成这些客户端 span，应使用独立采集路径，不能把上传请求的 SERVER span 误当作原生客户端 span；起止时间的时钟误差单独注明。无需为此先在 ArkTS 移植整套 OTel SDK。[S02][S04] 支持协议与采集能力；适配端是本项目设计
5. 业务正常响应返回 trace ID 给导演台做关联，响应字段不包含敏感用户信息；若网页脚本读取响应头，还需配置对应 expose-headers。无效 traceparent 交由标准 propagator 拒绝/新建上下文，不能当身份认证使用。[S02][S05] 加本项目设计

Vue H5 与 React 后台：用 OTel 浏览器 SDK 时，让它从活动 span 注入 header；如果浏览器异步上下文不稳，就在统一请求层显式管理操作→请求 span 的关系。跨域请求需允许 traceparent/tracestate，且只对白名单 API 传播；ArkWeb 资源页实际 origin、预检、凭证和上报通道均需在现有 App 中验证，不建议把 allowed-origin 改成通配符来掩盖问题。[S02][S03][S05]（查询：2026-11-16；接入方案待验证）

原生和 H5 接棒：桥接只传当前 action 的 traceparent、action_id 和必要标志；H5 提取后创建自己的 span，单次动作结束即释放上下文。并发动作各持独立上下文，不能做一个“全局最近 trace ID”，否则两个快速点击会串链。这个桥协议不传令牌给观测后端，也不把它当业务授权。

独立子进程：Node 发消息时把上下文 inject 到 envelope；子进程提取后建处理 span，再出自己的 OTLP，返回消息带 action_id。同步等待结果可以保持父子关系；异步后台任务可以用 span link 表达关联，不伪造连续占用时间。跨进程不会因为都叫 Node 就自动继承当前异步 context。[S05][S36]（查询：2026-11-16；具体协议为设计）

### 8.3 HiTrace 能不能映射到 OTel

事实：HiTraceId 在 ArkTS API 中包含 chainId（bigint）、spanId 和 parentSpanId（number）、flags；它是设备侧 TLS 中的上下文，官方说明有 begin/end 配对、标志位及自动传播约束。W3C 的 trace/span 字段则有固定字节长度与编码要求，flags 的定义也不同。[H01][H02][S02]（查询：2026-11-16）

判断：双轨关联可行性高；完整、通用、无损地把 HiTrace 自动转换为 OTel 的可行性尚未验证。日志里出现一个 HiTraceId，不等于能得到所有 span 的名称、起止时间、错误、资源属性和父子关系；HTTP header 透传也不是把 HiTrace 内部 trace 数据导出。

推荐先独立生成 W3C trace ID，把 `harmony.hitrace.chain_id`、`harmony.hitrace.span_id` 作为 OTel 属性，并在 HiLog 写同一个 action_id/trace_id；bigint 以字符串保留，避免转 number 丢精度。需要设备侧细查时，从导演台复制关联 ID 查本地日志。

不建议直接把 HiTrace 的十进制 ID 补零当 W3C ID，或把 flags 直接复制；若今后真做转换器，需要定义稳定的双向映射表、缺失 span 补全策略、异步边界、时钟与唯一性校验，再用并发动作与失败重试验证。本次没有验证这些，所以不会把“可做适配”写成“官方兼容”。

现成方案结论：未查到可直接用于本项目的官方 ArkTS OTel SDK，也未查到经过核实的 HiTrace→OTel 社区桥。检索范围是华为文档搜索的 OpenTelemetry ArkTS，以及 GitHub repository search 的 opentelemetry ArkTS/OpenHarmony/HarmonyOS、HiTrace OpenTelemetry 和 in:readme 扩展检索；直接关键词组合没有仓库命中，ArkTS 与 OTel 同在 README 的扩展检索有 17 个仓库，主要为技能/列表/多端项目，未识别出适配器。未覆盖所有 Gitee/OHPM 包和私有方案，搜索无命中不能证明世界上不存在。[H06]（查询：2026-11-16）

### 9.1 推荐组合的最小数据流

```text
原生操作 → 手工 traceparent + 客户端 span 适配 ┐
Vue H5 / React → OTel 浏览器 span            ├→ Node HTTP/Fastify span
                                             │    ├→ SQLite 手工 span
                                             │    └→ 推荐子进程 span（消息注入上下文）
所有 span → Collector → Jaeger 持久存储 → 公开查询 API → 只读查询适配层
网页 DOM 事件 → rrweb 文件，操作元数据 → 现有 SQLite → 导演台时间轴
只读查询适配层 + 脱敏事件摘要 → 只读 AI 解释 → 引用 span/日志证据
```

这是拟议设计，不是已部署架构。浏览器不直连带管理凭证的后端；ArkTS 适配也不依赖某个未验证 SDK。

### 9.2 会话时光机与只读 AI 从哪里读取

Jaeger 2 的官方 API 文档明确：推荐用稳定的 jaeger.api_v3.QueryService gRPC 查询，或者对应的稳定 JSON/HTTP v3 API；UI 使用的旧 `/api/` JSON 接口属于 internal，可能变化，不建议把 AI 写死在 UI 私有接口上。Jaeger 只保存 trace，不是日志库或回放存储。默认内存存储会在重启后丢 trace，因此“历史时光机”必须先验证持久化、容量与清理；不能靠一直不关容器冒充持久化。[S07]（查询：2026-11-16）

Tempo 备选可以用官方 `/api/traces/<traceID>`、v2 trace API 和 `/api/search`/TraceQL；OpenObserve 则需要按实施时版本单独验证查询接口，本次只核实到 OTLP 摄入及产品 UI，不把其 AI 读取 API 完成度写成已验证。[S08][S16]（查询：2026-11-16）

AI 的第一版只接受 trace_id 或 action_id，由项目自己的只读查询层取固定时间窗、固定数量的 span、错误和脱敏日志，再转换成简短证据包：服务、操作、起止时间、耗时、状态、父 ID、故障开关 ID与降级事件。输出格式建议是“看到的证据→能确认的位置→还缺什么证据”，每句话指回具体 span/event；例如“推荐请求 span 超时，商品查询 span 成功，系统记录了 fallback_used，所以本次慢在推荐子进程等待”。这是功能设计，本次没有调用模型。

只读查询层不提供 SQL 执行、文件任意读取、进程控制、故障开关或修改配置工具；没有证据时显示“未采集/无法判断”，区分超时与真正 CPU 卡死，不能仅凭最长 span 断言根因。Jaeger 当日文档虽已列出可选 AI/MCP 端点并默认关闭，但本项目不需要启用它们才能做只读助手，也未验证其模型配置及权限边界。[S07]（查询：2026-11-16；权限设计为本项目建议）

演示白名单请求可以全量采样并立即刷出事件；正式场景再按数据量选择采样。无论选哪种，AI 都应显示是否采样、trace 是否完整、客户端时钟是否可靠，避免把缺失的客户端/数据库 span 解释成“没发生”。

## 10. 五分钟演示剧本

这是推荐组合 A 的预定演示流程，并非本次已运行演示；两秒延迟是人为选的故障参数，不是产品性能数字。

| 时间 | 操作与观众依次看到的东西 | 当场可以讲的话 | 必须有的真实证据 |
|---|---|---|---|
| 0:00–0:45 | 导演台显示原生、H5、商家网页三个入口；先在鸿蒙推荐页点一次刷新，打开这一次 trace，看到原生请求→Node→数据库/推荐模块的父子瀑布图 | “同一串 trace ID 从手机带进后端；数据库用了 node:sqlite，所以这段是我在封装里补的埋点。” | Jaeger 真正存有客户端 span，不能只有 Node span 加一条伪客户端标签；界面上的数据来自刚才这次动作 |
| 0:45–1:30 | 在 H5、商家网页各做一次非资金操作，导演台按端筛选，分别打开对应 trace | “三个端都用同一套传播规则；每次点击是独立操作，不是把三次点击硬拼为一个 trace。” | 三个 service/client 标识不同，父子 ID 正确；同一动作从原生跳 H5 时才展示显式桥接 |
| 1:30–2:30 | 在导演台打开“推荐模块额外延迟 2 秒”，再次刷新；页面提示使用热门商品，商品页与购物车仍能读取；trace 展开后看到推荐等待、超时与降级事件 | “延迟超过我们设的请求预算就走降级，推荐失败没有堵住主购物服务；这个两秒是演练参数。” | 开关有 fault_id 和到期时间；超时、fallback_used 与正常查询 span 都存在；不能靠预制截图代替实际结果 |
| 2:30–3:15 | 点击“终止推荐子进程”，状态从退出→退避重启→健康检查通过；随后一个新请求恢复个性推荐 | “是监督代码重启子进程，Jaeger 只负责把过程记下来；我限制了重试次数，避免无限重启。” | 真实退出/重启/健康事件与对应 trace；新请求成功不等于旧请求自动重做；不要重发资金操作 |
| 3:15–4:10 | 打开刚才的 H5 会话时光机，播放到“刷新→等待→降级提示”，点击时间轴上的请求标记，跳到相同 trace；原生操作显示语义事件时间线 | “网页用 rrweb 重建 DOM；原生不是网页，所以我明确给它做事件流，没有宣称能自动录整套 ArkUI。” | replay_offset 与 action/trace 关联；敏感区遮挡；刷新或重启观测进程后历史还能读到 |
| 4:10–5:00 | 在这条 trace 上点“解释这次故障”，助手用白话说明推荐子进程等待超时、主查询成功、降级生效，并附 span/event 链接；界面同时标注可能缺失的证据 | “它只能读证据，不能替我改配置、执行命令或开启故障；哪里没采到它就说不知道。” | 来源链接能打开；只读接口无写权限；说明与实际 trace 相符；若模型未接入，应明确标“规则摘要演示”，不冒充实时 AI |

演示是否成功看四件事：三端各自打通上下文；一个非资金故障有可验证降级和恢复；事件流能定位到同一条 trace；解释只引用真实证据。性能提升多少、真实生产韧性如何，都不在这五分钟里凭空宣称。

待验证清单是未来落地的验收边界，不属于本次已完成的运行结果：

1. 固定 OTel/@fastify/otel/Collector/Jaeger 的实际发布版本与锁文件；用 Fastify5 ESM 加载方式验证只出一层合理 HTTP/Fastify span，避免插件启动过晚或重复自动插桩。
2. 验证原生并发点击、请求重试、H5 接棒与子进程消息后父子 ID 正确；客户端 span 确实进入后端，日志中 bigint 没有精度丢失；网络失败时业务不被遥测上传拖累。
3. 在现有 Pura 90 API24 中验证 ArkWeb 的 origin/CORS、请求头、浏览器 SDK、rrweb 遮挡、离线与页面退出批次；本次没有启动或操作任何模拟器。
4. 验证 node:sqlite 的手工 span、事务错误、慢查询与异步延迟演练的差异；不要把同步阻塞和人为等待混为同一种数据库瓶颈。
5. 验证推荐超时降级、子进程有限退避重启、健康检查、故障自动到期与紧急恢复；故障限制在非资金模块。
6. 验证 Jaeger 持久化、公开查询、事件/回放文件保留与清理；同一 action 的跳转与回放不是固定截图或硬编码 ID。
7. 验证只读助手的数据权限、超长/缺失 trace、采样与时钟提示；本次未调用任何模型，也没有输出实际 AI 排障效果。
