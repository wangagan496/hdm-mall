## 二、数据结构（迁移 007，数据库版本 6 → 7）

**payments（支付单，每次发起支付一条）**

| 字段 | 含义 |
| --- | --- |
| id | 支付单号，同时作为渠道的商户单号 |
| order_id、payer_id、amount | 订单、付款人、金额（分），发起时固定 |
| state | `pending` 确认中 / `succeeded` 成功 / `failed` 失败 / `closed` 已关闭 |
| created | T1 |
| grace_deadline | T1 + 10 分钟 |
| channel_paid_at | T2，只取渠道给出的交易成功时间 |
| closed_at | 关单时间 |
| callback_state、mismatch_count | 最近一次回调声明的结果；回调与查单相反的次数 |
| next_query_at、review_at | 下次查单时间；转人工的时间（为空表示未转） |

约束：同一订单最多一笔 `pending`（唯一部分索引）；`state` 只能是上述四种。

**refunds（退款单，每笔支付最多一条）**

| 字段 | 含义 |
| --- | --- |
| id | 退款单号，同时作为渠道的退款幂等键 |
| payment_id（唯一）、amount | 原支付单、退款金额 = 原支付金额 |
| reason | `late`（宽限后成功）/ `duplicate`（多笔成功）/ `cancelled`（确认中取消后成功）；第四步再加 `order-cancelled` |
| state | `pending` 退款中 / `succeeded` 已退款 / `failed` 失败可重试 |
| attempts、next_attempt_at | 已尝试次数、下次重试时间 |

**orders 表不改结构**。`paid_by`、`paid_at` 继续保存“有效支付”的付款人和 T2，现有收货、代收、权限判断不用改。

**迁移**：已付款的历史订单（`paid_by` 不为空）各补一条 `succeeded` 支付单，T1、T2 都取 `paid_at`。备份清单接受版本 7，统计 payments、refunds 行数；备份校验增加一项：每张已付款订单必须有且只有一笔有效支付。

## 三、支付渠道接口与模拟器

```text
PaymentChannel
  create(payment)            发起支付，返回渠道受理结果
  query(paymentId)           返回 { state: success|fail|unknown|closed, paidAt?, amount? }
  close(paymentId)           关单，返回关单是否成功；已扣款时返回 success 与 paidAt
  refund(refundId, paymentId, amount)  返回 success|fail
```

- `buildApp` 接收 `paymentChannel`。测试模式默认用模拟器；正式环境没有配置渠道时，发起支付返回 503“当前环境未接入支付渠道”，与现在一致。
- 回调签名：HMAC-SHA256，密钥取环境变量 `PAYMENT_CALLBACK_SECRET`。正式环境配置了渠道却没有密钥时拒绝启动。
- **模拟器**由测试夹具控制，凭证与第一步夹具相同。对每笔支付（或“下一笔”）可以预设：
  - 结果：成功（指定 T2）、失败、一直未知、关单时已扣款；
  - 查单结果：与回调一致、与回调相反、缺少 T2；
  - 退款：成功，或前 N 次失败。
  - 模拟器还提供 `signedCallback(paymentId, 覆盖项)`，生成合法回调；测试可以重复、乱序、改签名、改金额后自己发送。
- 不预设时，模拟器在发起支付后立即发出成功回调，T2 = T1。这样手动演示和现有设备回归的体验不变。
- 真机夹具通过 `/__test/fixtures/payments` 设置预设，供 S3 使用。

## 四、接口

| 接口 | 说明 |
| --- | --- |
| `POST /member/order/:id/payments` | 发起支付。校验付款权限、订单待付款、未超过付款时限（必须早于 T0 + 15 分钟）、没有确认中的支付、金额与订单一致。返回支付单号和状态 |
| `GET /member/order/:id` | 订单展示新增字段，见第六节 |
| `POST /member/order/:id/payments/refresh` | 用户点“刷新”时立即对确认中的支付查一次单，最多每 5 秒一次 |
| `POST /payments/callback` | 渠道回调，不带用户凭证。验签失败返回 401；订单号、支付单号或金额不符返回 400；两者都记录日志，订单不变 |
| `PUT /member/order/:id/cancel` | 原有接口，行为按第五节扩展 |
| `GET /merchant/payments/review` | 商家分页查看转人工的支付单 |
| `POST /merchant/payments/:id/requery` | 商家对转人工的支付单立即查一次单 |
| `PUT /merchant/payments/:id/resolution` | 商家登记线下核实结果：`paid`（必须带扣款时间）或 `unpaid`；必须带原因和请求号，重复提交只生效一次，留操作记录 |
| `POST /merchant/refunds/:id/retry` | 商家核实列表以 `kind=refund` 展示转人工退款；商家带 UUID 请求号重试原退款单，重复请求只执行一次并留操作记录 |
| `POST /member/order/:id/mock-pay` | 保留，仅在模拟支付环境可用：内部改为“发起支付 + 模拟器立即成功”，走同一套状态机。现有测试和设备脚本可以继续用它准备已付款订单 |

## 五、处理规则

所有状态变化都在一个数据库事务里完成，事务里先重新读取订单和支付单的最新状态。

1. **回调**：验签和金额通过后，记录回调声明的结果，并立即对这笔支付查一次单（见第九节 P2）。
   - 查单结果与回调一致：按查单结果处理。
   - 查单结果相反，或缺少 T2：保持确认中，`mismatch_count` 加一，1 分钟后再查；连续两次相反，转人工。
   - 同一支付单已处于终态时，重复或过期的回调只记录，不改状态。
2. **查单得到成功**（有 T2）：
   - T2 不晚于宽限截止，且订单未取消：支付单记为成功，再按第 4 条选出有效支付。
   - T2 晚于宽限截止，或订单已取消：支付单记为成功，同时创建退款单。
3. **查单得到失败**：支付单记为失败。渠道明确返回 `closed` 表示我方已关单且渠道确认未扣款，按明确未付处理。还在付款时限内，订单回到待付款，可以再付；已过付款时限，订单取消，库存只释放一次。若回调声明成功而查单返回 `closed`，按 K13 作为回调与查单相反处理，计入 `mismatch_count`，连续两次转人工，不直接判失败；已是本地 `closed` 且没有相反成功回调时，查单返回 `closed` 则停止查单。失败的支付单之后若查到成功（渠道更正），按第 2 条处理；成功的支付单不会再变回失败。
4. **多笔成功**（第九节 P3）：**先被系统确认成功的那笔为有效支付**，订单的 `paid_by`、`paid_at` 取它，之后再确认成功的每笔各建一条退款单；有效支付一旦确定不再更换。订单已取消时，所有成功支付都退款。
5. **超时**：
   - 订单到达付款时限、没有确认中的支付：取消，释放库存（与现在相同）。
   - 支付到达宽限截止：先关单，再查单，按第 2、3 条处理；仍然未知时保持确认中，按 1、2、5、10 分钟递增间隔继续查，最长 30 分钟一次。
   - 发起后 24 小时仍未知：转人工，记录 `review_at`，订单显示核实提示；库存继续保留，直到人工处理或查到结果。转人工只增加商家提醒，不停止自动查单；继续按递增间隔查询，最长 30 分钟一次，查到确定结果后按第 2、3 条自动处理并清除核实状态。
6. **确认中取消（K12）**：只有下单人可以，且要先弹窗确认：“付款可能已经成功。取消后，如已扣款，¥金额将原路退回付款账户。确定取消吗？”确认后订单取消，关闭支付单，库存释放一次。之后这笔查到成功，按第 2 条退款。
7. **退款**：退款单创建后由 `reconcile` 立即调用渠道。失败则记为失败，按 1、5、30 分钟、之后每小时重试，重试沿用同一个退款单号。自退款单创建满 24 小时仍未成功，记录转人工时间并停止自动重试，给下单人和付款人各生成提醒（同一人只生成一条）；商家核实列表以 `kind=refund` 展示，可带请求号重试同一退款单，重复请求只生效一次并记录操作，重试成功后记为已退款。
8. **执行时机**：读请求只做数据库内的状态变化，不调用渠道。查单、关单、退款由后台定时任务执行（复用现有 30 秒定时器）；回调、刷新、商家定向重试等通过 `reconcile` 立即触发对应任务；测试通过 `payments.reconcile(now)` 直接驱动，配合可控时钟，不需要真实等待。

## 六、用户看到什么

付款相关的状态，用户最怕三件事：钱扣了没、会不会扣两次、钱什么时候回来。每条提示都要回答这三点里相关的部分，并告诉用户下一步能做什么。

| 场景 | 用户看到的 | 用户能做的 |
| --- | --- | --- |
| 刚点完付款，结果还没回来 | 付款结果页显示“正在确认付款结果，请勿重复付款”，**页面自动刷新**（每 2 秒一次，持续 30 秒），不用用户手动点 | 等待；或离开页面，结果会显示在订单里 |
| 30 秒后仍未确认 | “付款结果仍在确认中，可能需要几分钟。不会重复扣款，确认后订单会自动更新。” | 手动刷新；回到订单；取消订单（见第五节第 6 条） |
| 确认中的订单 | 订单列表放在“待付款”分页，标签“确认中”；**不显示付款倒计时**，避免用户以为还要再付一次 | 同上 |
| 付款失败，还在时限内 | “付款未成功，未扣款。可以重新付款。”继续显示倒计时 | 重新付款 |
| 付款失败，已超时 | “付款未成功，订单已超时取消，未扣款。” | 重新购买 |
| 宽限期后才扣款、确认中被取消后扣款、多扣了一笔 | “这笔付款 ¥金额 已原路退回 / 正在退回付款账户”，写明是哪一笔（付款时间、付款人） | 查看退款状态 |
| 退款失败重试中 | 自动重试期间：“退款处理中，系统会自动重试，无需操作。”；转人工后：“退款遇到问题，我们正在人工处理。可以进入帮助与客服咨询。” | 自动重试期间无需操作；转人工后进入“帮助与客服”页 |
| 转人工核实 | “我们正在核实这笔付款。如已扣款，核实后会原路退回或完成订单。” | 取消订单；进入“帮助与客服”页（已有页面） |

**亲友代付**：付款的亲友也必须能看到自己那笔付款的状态和退款。现在亲友只有在成为订单的有效付款人时才能查看订单（`orders.ts` 的 `canRead`），如果亲友那笔被退款，亲友就看不到了。本步改为：在这张订单上发起过支付的人，都能查看订单的付款与退款部分；能不能看商品和地址，仍按现有规则。

**提醒入口**：有退款或需要核实的订单，“我的”页订单入口和订单列表显示红点，用户打开订单后消失（见第九节 P1）。

### 卖家看到什么

卖家最怕两件事：发了货钱却没收到或被退回；库存被卡住卖不出去。本项目里商家也是唯一能处理“转人工”的角色。

| 场景 | 卖家看到的 | 规则 |
| --- | --- | --- |
| 买家付款确认中 | 待发货列表里**没有**这张订单 | 订单停在待付款，只有确定了有效支付才进入待发货（现有列表按 `state=2` 查询，本步保持） |
| 发货 | 只能对有有效支付的订单发货 | `ship` 在事务里再检查一次存在成功的有效支付单，缺失时拒绝，防止数据异常时发出没收到钱的货 |
| 迟到成功、多扣一笔 | 订单不进入待发货，也不改变已发货订单的付款人 | 这些钱不属于卖家，系统自动退给买家，不需要卖家操作 |
| 转人工核实 | 商家页新增“待核实付款”列表：订单、金额、付款人、发起时间、已查单次数；可以重新查单或登记核实结果 | 见第九节 P4 |
| 库存被确认中订单占用 | 库存页的“占用”包含确认中订单 | 见第九节 P5 |

不做：对账报表、渠道手续费、结算到账。

## 九、已定决策

以下各项已于 2026-11-05 按推荐确认。

| 编号 | 问题 | 决定 |
| --- | --- | --- |
| P1 | 没有消息推送，用户怎么知道钱退了或在核实 | 订单入口和订单列表显示红点，订单里写清金额、哪一笔、退到哪里；核实中的订单引导到已有的“帮助与客服”页。消息推送以后再做；转人工由商家按 P4 处理 |
| P2 | 回调到达后，要不要先查单确认再生效。K13 要求“回调与查单相反时以查单为准”，只有每次回调都查单才能发现相反 | 每次回调都先查单再生效。用户多等一次查单的时间（通常一两秒），结果页本来就会自动刷新，感受不明显；换来的是不会先显示成功又变成失败 |
| P3 | 同一订单多笔都扣款成功时，保留哪一笔。方案第三节现在写的是“保留 T2 最早的一笔” | 改为**保留先被系统确认的那笔**，之后确认的都退款。按 T2 最早保留，会出现“页面已显示你付款成功，过一会儿又改成亲友付款、你的钱被退回”；付款人变了，谁能确认收货也跟着变。已同步修改方案第三节判定规则第 4 条 |
| P4 | 转人工后商家能做什么。只能看不能处理，订单就会一直卡着 | 商家可以点“重新查单”；渠道仍查不到时，商家可以按线下核实结果登记“已扣款（填扣款时间）”或“未扣款”，必须填原因，带请求号防重复，留操作记录（做法同库存调整）。登记后按第五节第 2、3 条处理，不能直接改订单状态 |
| P5 | 结果一直未知时库存最长占 24 小时（K4、K14），热销商品可能因此少卖 | 保持 K4：查到结果前不释放。理由是先释放再查到成功，就可能没货可发，只能退款，对买家更伤。占用数量在库存页显示，方便卖家知道原因 |

## 十、本轮不做
