## 商品详情接口直接返回商品资料（已实现并验证）

当前情况：`GET /goods?id=商品编号` 现在直接返回 `{ id, name, ... }` 商品对象；唯一的客户端调用链是 ArkTS 端 `home.ets` 发起请求、`RequestAxios.ets` 读取响应正文。

优化点：商品详情已去掉 `{ code, result }` 包装，ArkTS 页面直接收到商品资料；`RequestAxios.ets` 仅对该接口采用直接返回逻辑，其他接口继续解包 `result`，接口改造已实现并验证。

实施与验证：同步调整商品详情的请求封装，保留请求地址、参数、token 传递、有限重试和失败提示规则；其他接口仍使用 `{ code, result }`，不能删除公共封装的原有处理。验证详情成功、缺少编号、商品不存在和网络失败，以及订单等未改接口的返回值仍正确；收益是简化数据结构，不预设性能提升。

## 服务端确认登录过期后清理本地登录状态（已实现，自动检查通过）

当前情况：`PhoneAbility.ets` 启动时只检查本地 token 是否存在，然后把保存的用户资料恢复到 App 当前状态，并不向服务器确认 token 是否仍有效。`RequestAxios.ets` 请求被服务器以 HTTP 401 拒绝时会显示服务器提示并返回失败，但不会清理手机持久存储或 App 当前用户状态，因此界面可能继续保留旧登录资料。

优化点：仅在服务器明确返回 HTTP 401、确认当前请求 token 已无效后，清除手机本地保存的登录资料并将 App 当前用户状态更新为空用户，同时提示用户重新登录；普通断网、超时或服务器错误时保留已有登录状态，不把无法联网误判为退出登录。

实施要点：退出流程已由 `UserSession.logout()` 清理持久资料、当前用户状态并更新购物车角标，实施时复用合适的现有清理逻辑，避免网络层依赖反向引用造成模块循环。处理并发请求时避免重复弹出登录提示；如果旧 token 的请求晚到，不能清除用户刚刚重新登录后保存的新 token。

解决的问题（预期）：服务器确认登录已经过期后，App 不再继续显示旧头像或把用户误认为仍登录，并提供清晰的重新登录入口；网络暂时不可用时保留登录信息，恢复网络后仍可重试。

验证要点：启动时本地有过期 token、接口返回 401 后验证持久资料被清理、App 当前用户状态变为空并提示登录；网络超时、断网和 5xx 时确认登录状态保留；并发 401 只提示一次；旧请求延迟返回 401 时不清除随后新登录得到的 token。

2026-10-27 综合审查补充：H5 的 `shoph5-vue3/src/api/index.ts` 遇到 401 目前也只提示，不清理登录。实施时两端采用同一套会话失效规则，H5 通知原生处理并清空对应网页资料；按发起请求时的会话核对，不让旧请求清掉新账号。与文末“退出登录、服务端会话与角标统一收尾”“H5 个人资料保存与原生同步一致性”配合，避免各处重复实现注销。

## 个人资料接口直接返回 token（已实现，自动检查通过）

当前情况：`GET /member/profile` 返回昵称、头像等资料，未返回 token；`shoph5-vue3/src/stores/profile.ts` 从 App 读取用户信息，与接口资料合并后再明确保留 App 的 token，阅读时需要在两个数据来源之间来回确认。

优化点：让个人资料接口在鉴权通过后，把本次请求使用的有效 token 和最新资料一起返回；H5 直接使用这份完整数据，简化资料合并及单独保留 token 的代码。此项是用户提出的待优化方案，尚未修改接口或客户端实现。

实施要点：服务端会话表只存 token 摘要，不能从数据库还原原值，返回值应来自本次已鉴权的请求；查询资料不重新签发 token，也不延长有效期。请求发出前仍需从 App 取得登录凭证，接口返回 token 不能替代这一步；直接替换页面数据前需确认接口已覆盖页面与原生同步需要的字段。

解决的问题（预期）：让网页从同一份接口结果得到最新资料和当前登录凭证，减少前端合并步骤，使“查询资料后直接展示”的流程更直白。

验证要点：有效登录请求返回的 token 与请求凭证一致，缺失或失效的凭证仍被拒绝；查询不改变会话有效期，加载及保存资料后的字段和 App 登录状态保持正确。

## 本地快速重排与后端全量排序结合（已实现并验证）

优化点：在关键词、分类等筛选条件不变时，切换排序先按新规则重排已加载商品，让页面立即响应，并明确提示“仅已加载商品已重排，完整排序更新中”；同时更新搜索编号，重置分页与去重状态，从第 1 页请求后端对全部匹配商品排序后的结果。本地与后端采用一致的排序规则，后端结果返回后替换临时列表，后续分页只追加新排序的结果，旧请求及其异步处理不能再更新页面。后台更新失败时保留临时结果，说明完整排序更新失败并提供重试入口，不把局部排序呈现为全部商品的最终顺序。

解决的问题（预期）：结合本地排序的快速反馈与后端排序覆盖全部商品的能力，减少切换排序后等待接口才看到变化的情况，同时解决未加载商品无法参与本地排序的问题；避免新旧排序结果混入同一列表。该方案主要改善响应体验，不默认减少请求次数，实施前需结合实际等待时间评估收益与新增状态管理成本。

优化点：

重构方向：把“检查库存并扣减”和“保存订单及明细”拆为职责清楚的业务方法，由下单入口统一控制同一个事务和数据库连接；方法内部不另行提交或开启独立事务，购物车变更仍参与原事务。下单入口直接呈现业务顺序，避免为了分层增加无用的类、服务或通用操作框架；目标是提升可读性与修改局部规则的便利性，不承诺减少数据库操作或提高并发性能。

边界与验证：保持服务端价格计算、订单商品快照、请求编号查重、库存条件扣减、15 分钟待支付期限和整单失败回滚的行为；核对库存不足、扣库存后写单失败、订单明细或购物车操作失败时均不留下部分提交，同一请求重试仍返回原订单。真正支付平台应在建单事务提交成功后调用，结果确认和必要退款另行处理；当前 `pay()` 仍为模拟支付，本轮没有授权接入真实扣款。用户要求先记优化点，只补文档，未拆方法或执行重构后的验证。

## 订单改址、补运费与失败退款（新增功能，不在本轮）

当前范围：这是学习讨论中确认的扩展方案，尚未实现；当前项目使用模拟支付，不能把模拟补款或退款结果描述为真实资金到账。

优化点：

1. 先确认原订单：下单请求没有收到回应时，先确认服务端是否已经创建订单；确认原订单后在原订单上申请改址，不通过更换下单请求编号来修改地址，避免重复创建商品订单。结果仍不确定时保留查询／重试入口，不直接判定订单不存在。
2. 按履约进度判断能否改址：已创建、已付款不一律禁止修改，由服务端检查仓库是否已处理及配送是否允许变更；已发货需确认物流能否改派，不能只更新客户端显示。申请时及实际生效时都核对条件，防止补款期间订单已进入不能改址的阶段。
3. 重新核对配送条件：核对新地址、收件人和电话，重新计算配送范围与运费；向用户展示新地址、运费差额和处理结果，用户确认后继续，不擅自改变原订单的商品和数量。
4. 关联原订单补收运费：需要补款时，在原订单基础上新建一笔只收运费差额的“补运费单”，关联原订单和本次改址申请，不重复生成商品或发货任务；用户确认并补款成功后，再完成地址变更，明确展示“待补款／改址处理中／改址成功”等状态。
5. 查询结果后再重试：补款成功但未收到改址成功回应时，先查服务端实际状态；已经改好则刷新页面，确实未改且仍允许改址才重试同一次申请，并沿用请求编号。同一次补款、改址或退款重试不能重复扣款、重复退款或重复执行变更。
6. 无法改址则退回补款：如果服务端明确无法完成改址，退回本次补收的运费，原订单继续保留原地址；显示退款进度，确认退款完成后才显示“退款成功”。退款失败或结果不确定时继续查询和处理，不能把未完成的退款当成已经退回。

解决的问题（预期）：减少用户在下单后无法更正收货地址的情况；避免结果不确定时重新下单产生重复订单；避免跨地区改址后的配送范围、运费与订单不符；避免补运费成功但改址失败后资金没有退回，以及重复重试造成重复扣款或退款。

实施与验证：需要客户端、订单服务、仓库／物流状态及支付退款能力共同配合，先在模拟流程验证；重点覆盖下单回应丢失、重复提交改址、补款期间订单发货、补款成功但改址回应丢失、改址明确失败及退款重试，检查商品订单不重复、运费差额不重复收退、最终地址与配送状态一致，用户看到的进度与服务端一致。

## 取消订单结果确认与有限自动重试（已实现，自动检查通过）

当前基础：`server/src/orders.ts` 的取消流程已在数据库事务内检查订单归属和状态；已取消的订单直接返回原订单号，不重复归还库存，只有未付款订单可以继续取消。`server/src/database.ts` 将取消状态变更和库存归还一起提交，出错时一起撤销。本次待优化的是客户端的结果确认与自动重试体验，不是重新增加一套服务端取消流程。

优化点：

1. 只延续用户已确认的取消操作：取消请求遇到网络超时等结果不明的情况时，可以自动重发同一订单的取消请求；不能因为用户打开订单页面，就擅自发起取消。
2. 返回页面先确认状态：用户退出后重新进入，先查询服务端订单状态；已经取消则展示取消结果，已付款等不再允许取消的状态则停止取消操作，仍未付款且保留了用户的取消意图时才继续处理。
3. 有间隔、有次数上限地重试：同一订单同一时间只发一个取消请求，失败后间隔重试，并设置最大次数，避免连续点击与自动重试叠加；重试间隔和次数在实施时根据实际网络情况确定。
4. 明确结果就停止：取消成功或确认已经取消时结束重试并刷新页面；服务端明确拒绝时停止，展示用户能理解的原因；不能把业务拒绝当作网络问题反复提交。查询和取消结果仍不确定时，保留未知状态，不擅自显示取消成功或失败。
5. 提示直白并保留查询入口：重试过程中显示“正在确认取消结果”；达到重试上限仍无法确认时，显示“取消结果待确认，请稍后查询”，提供“重新查询”按钮，减少用户反复手动取消的负担。

解决的问题（预期）：避免把“没收到取消回应”误判为“取消失败”；在服务端已有防重复取消和库存事务保护的基础上，减少短暂网络异常导致的手动操作，同时避免无限重试、业务拒绝后继续重试以及重复归还库存。

验证要点：覆盖取消已成功但回应丢失、请求尚未到达服务端、重试前订单已经付款、连续点击与自动重试同时触发、持续断网达到上限，以及退出再进入页面；确认同一订单库存只归还一次，明确成功或拒绝后停止重试，未知结果始终显示待确认且可重新查询。

## 自动确认收货与售后计时衔接（新增功能，不在本轮）

当前范围：学习讨论中的扩展方案，不代表现有功能；“物流签收后七天自动确认收货”是本项目拟定规则，不是所有购物平台的通用规则。

优化点：

1. 从物流签收开始计时：物流签收不直接等于买方确认收货，保留七天供用户取件、检查商品；不从发货时间起算，避免运输时间占用检查时间。由服务端记录签收时间和确认期限，执行自动确认前核对订单是否仍待收货。
2. 售后期间暂停：用户已申请退货且尚在处理时，暂停自动确认收货；售后与原订单联动，不能因为进入另一条流程就继续按原期限自动确认。
3. 撤销售后后保留确认时间：建议记录暂停时剩余的时间，撤销后继续计算；不因每次撤销都重新给完整七天，避免反复申请和撤销使订单无限延期。如需最低宽限时间，采用一次性、有限的规则，具体时长实施前再确定。
4. 明确收货与完成的区别：自动确认收货后按项目订单流程进入待评价，不直接把订单标成已完成，也不把确认收货等同于商家已经收到货款。

解决的问题（预期）：减少用户忘记确认收货导致订单长期停留的问题，同时避免运输耗时、售后处理中或刚撤销售后时过早确认收货；防止反复撤销售后重置期限造成无限延长，让用户检查商品的时间和订单后续处理都有明确规则。

验证要点：覆盖运输超过七天、物流重复推送签收、期限到达时正在售后、撤销售后恢复剩余时间、反复申请与撤销、用户已手动确认，以及自动确认与申请售后同时发生；确认计时不重复重置，售后期间不自动确认，同一订单只确认一次。

## 商家结算结果确认与防重复打款（新增功能，不在本轮）

当前范围：商家结算属于扩展设计，当前模拟支付不能证明真实打款或到账；实际接入时需要支付渠道提供结果查询和防重复打款能力。

优化点：

1. 分开记录订单状态与结算状态：确认收货与向商家打款分别处理，订单已确认收货不表示商家已到账；打款超时不把已确认收货的订单退回待收货。具体何时允许结算，按售后情况及最终业务规则判断。
2. 超时先查结果：使用本次打款编号向支付渠道查询；确认已到账，就补记结算成功，不再转账；查询仍无结果时保留“打款结果待确认”，不能把超时当作明确失败。
3. 确认可重试后再补发：仅在渠道确认未成功且允许重试时，按渠道规则沿用同一笔业务打款标识重试，并限制次数和间隔；不能直接新建另一笔打款绕过防重复保护。成功通知、查询结果与重试结果都对应同一笔结算记录，重复通知不重复入账或触发转账。

解决的问题（预期）：避免订单已确认收货却因打款异常回退状态；避免商家实际已到账、平台因回应丢失再次转账；让未到账、已到账和结果不确定分别可查、可继续处理。

验证要点：覆盖已到账但成功回应丢失、明确打款失败、渠道查询超时、重复成功通知、并发重试及服务重启后恢复查询；确认同一笔结算不重复打款，只有确认到账后才记录成功，订单与结算状态分别准确。

## 待付款倒计时改用开机时长并在回到前台时校准（已实现，自动检查通过）

当前情况：`OrderView.ets`、`OrderDetailView.ets`、`PayView.ets` 拿到订单时用 `Date.now()` 记下手机时间，`OrderCountdown.ets` 每秒用“现在的手机时间 − 记下的时间”算出已过去的秒数，再从服务端给的剩余秒数里减掉。用户在设置里改手机时间，页面倒计时就会跟着变：调快 5 分钟，剩余 10 分钟会直接显示成 5 分钟；调慢则会多显示时间。

优化点：

1. 计时改用开机时长：把 `Date.now()` 换成 `systemDateTime.getUptime(systemDateTime.TimeType.STARTUP)`，记录时间和每秒计算都用它。按鸿蒙官方文档，它表示自系统启动以来经过的时间，包括深度睡眠时间，不受用户修改手机时间影响；锁屏睡眠期间也继续累计。该接口从 API 10 起提供，本项目 `compatibleSdkVersion` 为 API 24，可以直接使用。三个页面和倒计时组件统一改，避免一处用手机时间、一处用开机时长。
2. 回到前台时重新查询：页面从后台回到前台时，向服务端重新查询订单，用最新的剩余秒数和新的记录时间重新计算，纠正后台期间的误差；订单如果已经到期或取消，直接按服务端状态显示。`OrderView.ets` 和 `OrderDetailView.ets` 已有 `onShown` 刷新，实施前需确认它在 App 从后台回到前台时是否触发，不触发就另外接入 App 回到前台的通知。
3. 服务端仍是唯一依据：倒计时只负责显示，能否付款始终以服务端订单状态和到期时间为准；页面显示到期后提示等待系统处理或刷新，不在手机上自行认定订单已取消。

解决的问题（预期）：避免用户修改手机时间导致倒计时显示错误，减少“页面显示还有时间，实际已经到期、付款被拒”的情况；切到后台再回来时，倒计时与服务端保持一致；不需要让 App 在后台一直运行定时器，不额外耗电。

验证要点：覆盖手机时间调快和调慢、切到后台若干分钟再回来、锁屏后再解锁、在后台期间订单到期、回到前台时网络失败，以及订单列表、订单详情和支付页三处倒计时；确认显示的剩余时间与服务端一致，修改手机时间不影响倒计时，到期后付款仍由服务端拒绝。

## 下载任务创建失败时结束等待并传出错误（已修复，待设备验收）

原问题：`DownLoadManager.ets` 的旧 `downloadSingle()` 使用 `new Promise(async (resolve, reject) => ...)`，在异步执行函数中等待 `request.downloadFile()` 创建任务，却没有把创建阶段的异常接到外层 `reject`；旧实现只在已建立任务的 `fail` 事件中报告下载失败。创建任务时的异步失败会落到内部异步函数返回的 Promise，而外层 Promise 仍未结束；批量下载的 `.catch(() => null)` 因此接不到这个失败，等待该项的 `Promise.all()` 也无法正常完成。影响的是这条图片下载与后续卡片推送链，不能据此声称整个首页或 App 卡死。

已有证据：2026-10-28 学习时提取实际 `downloadSingle()` 方法，仅移除类型标注并替换平台依赖，在 Node 内存中模拟两种失败；创建任务直接拒绝时，40ms 观察窗口内外层仍为 pending，并捕获内部未处理拒绝；对照组创建任务成功后触发 `fail` 事件，外层正常拒绝并返回“下载失败”。结合源码可确认创建错误未接到外层等待，观察窗口不是业务超时设置；模拟未访问网络、未写图片或测试脚本，未做设备复现。

本次实现：2026-10-28 将单张方法命名为 `downloadImage()`，主流程按“创建下载任务 → `waitForDownload()` 等待下载完成 → 返回图片路径”展开；`downloadImage()` 本身为异步方法，创建失败直接向调用方传出，普通 `new Promise` 只保留在 `waitForDownload()` 内部，并注释成功与失败的处理。批量方法继续允许部分成功、按输入顺序返回成功图片，失败项仍转为 `null` 后过滤；批量和单张方法分别等待各自结果，未添加前后状态标记。公共调用方法、下载路径规则与卡片推送流程未变，缓存复用、失败文件清理和卡片重试未在此次实施。

修复后验证：本轮先将修改前实际源码转译为 JavaScript、替换平台依赖，在 50ms 观察窗口复现创建失败后仍等待及未处理拒绝，再对修改后实际源码完成 8 项隔离检查：创建任务拒绝、创建时同步抛错、任务下载失败、成功返回路径、批量部分失败与乱序完成后保持输入顺序、全部失败、空列表、无未处理拒绝，全部通过；创建错误保留原对象，下载失败保留原提示。观察窗口不是业务超时设置，没有访问网络、写图片或增加测试脚本；已核对本机 SDK 的 `downloadFile(): Promise<DownloadTask>` 与 `DownloadTask` 声明。真实平台回调、设备下载和桌面卡片交互尚未验收，隔离检查不等同于设备验证。
