# 库存流水与迁移验收

日期：2026-10-28；以下记录版本 3 的历史验收基线，范围为下单、取消、到期处理与库存查询，当时不包含退款入库、人工调库存和新商家页面。

后续进展：版本 4 新增 adjust 流水及 reason 字段、商家库存调整接口和原生入口，保留原流水编号及不可修改约束；人工调整与库存同事务提交，详情见 [商家库存调整验收](商家库存调整验收.md)。当前版本 5 进一步迁移头像引用，不改变库存规则，见 [头像地址迁移验收](头像地址迁移验收.md)；当前服务端 52 项全部通过，备份接受版本 2、3、4、5，下文 42 项测试仍为版本 3 阶段的历史证据。

## 已实现行为

每次实际库存变化记录规格、订单、数量变化、变化后可售库存、业务编号、操作人和时间；下单为负数，取消和到期归还为正数，系统到期操作人为空并单独标记原因。

库存、流水、订单和购物车修改共用原业务事务；流水失败时整笔回滚；同一订单同一规格最多一次下单扣减、一次取消或到期归还，取消与到期共用释放编号；重复请求不会重复记录或增加库存。

数据库禁止修改或删除已有流水；后续人工调整必须新增有原因和操作人的调整记录，不能改旧记录来掩盖差异；本轮尚未提供人工调整接口。

| kind | 含义 | delta | balance | 操作人 |
| --- | --- | --- | --- | --- |
| opening | 首次创建规格或旧库迁移时的可售库存基线 | 当时库存，可为 0 | 当时库存 | 空 |
| reserve | 下单占用 | 负的购买数量 | 扣减后库存 | 下单人 |
| cancel | 下单人取消未付款订单 | 正的归还数量 | 归还后库存 | 取消人 |
| expire | 未付款到期取消 | 正的归还数量 | 归还后库存 | 空，系统操作 |

实现位置：server/src/inventory.ts、orders.ts、catalog.ts；表结构及约束见 server/src/migrations/003-inventory.sql。

## 查询与核对

仅商家可使用以下接口，匿名返回 401，买家返回 403；接口不提供库存修改能力。

| 接口 | 用途 |
| --- | --- |
| GET /merchant/inventory?page=1&pageSize=10 | 查看规格、商品名称、实际库存、流水合计及差额，支持 skuId 精确筛选 |
| GET /merchant/inventory/:id/movements?page=1&pageSize=10 | 按最新记录在前分页读取规格流水，包含订单编号与操作人编号 |

分页上限为 100，结果沿用 result 包装；difference 等于实际库存减流水合计，正常为 0；发现差异只展示，不自动改库存或补造流水；数据查询按数据库分页，未新增整库加载的页面。

库存差异核对示例：初始化库存 20，下单 2 记录 -2、余额 18，取消记录 +2、余额 20；重复取消不增加行数；备份和恢复校验也检查库存与流水合计，不一致会返回失败，不能把有差异的快照当作已验收恢复结果。

## 数据库升级与备份兼容

版本 3 阶段程序读取版本 1、2 时逐步升级到 3；版本 3 新增 inventory_movements，迁移脚本与版本号在同一事务内提交；失败回滚并关闭连接，修复原因后可以再次启动，未支持的更高版本拒绝打开；当前版本 5 在此基础上继续逐版升级。

旧数据以迁移时的实际可售库存建立 opening，不倒推订单来虚构历史；例如旧订单已占用 2 件、当前库存为 18，迁移只记基线 18，后来取消记 +2 得到 20；不能把“没有迁移前扣减记录”当作漏记本轮流水。

新规格的初始化库存由商品初始化事务同时写入 opening，重复启动不会重新补库存或重复生成基线；已有商品和订单均保留。

备份工具继续接受版本 2 的旧备份，同时支持版本 3 的快照；清单版本须与实际数据库一致；恢复版本 2 后，由当前服务首次启动升级；版本 3 的恢复演练增加库存流水表，当前逐行核对 12 张业务表，会话表仍单独清空。

实际升级前先保留可校验的旧版本备份，在隔离目录验证兼容代码和数据后再安排切换；旧程序不能直接打开版本 3，应用回退须同时使用对应的旧快照并核对升级后新增交易，不能只把 user_version 改回 2；本轮只升级临时测试库，没有重启或迁移现有开发服务的数据。

## 已执行验证

执行 `pwsh -File scripts/verify-server.ps1`，类型检查与 42 项服务端测试全部通过；其中本轮新增 9 项库存专项，补充原有事务故障检查中的流水回滚断言，并扩展备份恢复检查。

| 验证 | 结果 |
| --- | --- |
| 初始化、重复下单、重复取消 | 基线不重复，变化数量、余额、操作人及业务编号正确 |
| 到期与付款 | 多次到期扫描只归还一次，已付款订单不归还库存 |
| 下单和取消故障 | 流水写入失败时库存、订单、购物车和此前写入的其他规格流水一起回滚 |
| 批量到期故障 | 第二笔流水失败时同批订单全部回滚，重试后各归还一次 |
| 商家接口 | 买家和匿名拒绝访问，分页和规格筛选有效，实际库存被改动时显示差异 |
| 最后一件并发 | 两次 HTTP 下单只有一次成功，只为成功订单记流水 |
| 流水约束 | 修改、删除和重复释放均被数据库拒绝 |
| 历史迁移 | 版本 1 原有商品保留；版本 2 备份可恢复到新目录再升级，旧待付款订单仍可正确取消，重启不重复基线 |
| 迁移失败 | 制造迁移后半段对象冲突，版本和新表全部回滚，移除冲突后迁移成功 |
| 备份与恢复 | 版本 3 恢复后 12 张业务表一致；重新填写哈希也不能绕过库存与流水一致性检查 |

退款、实际退货验收、人工调库存、操作后台和生产负载仍不在本次完成范围；本轮保证现有变动路径可追溯，不代表已具备完整仓储或售后体系。

## 可复用的验证方法

给已有库存补流水时，从实际可售库存建立有明确起点的基线，再让每次变动与原业务事务同时提交；用第二笔写入失败证明前一笔也会回滚，用旧待付款订单跨迁移取消证明历史库存不会重复释放；迁移失败检查必须同时核对版本、表结构和原数据。
