# 备份恢复操作与验收

## B包：定时备份、存储上传与下载恢复（2026-11-11）

当前数据库版本为17。迁移017新增开票、评价处理及客服会话、留言、照片登记；备份校验覆盖归属、订单关联、读到位置、图片与处理状态。版本2–16仍按原版本规则校验，旧v16兼容样本保留v16断言，恢复后首次打开再迁移到17，不把旧数据当成17结构。

### 调度与存储配置

- `BackupStore`定义put、list、delete；可读实现另有get供下载恢复使用。`LocalDirectoryStore`用于本机冷备份与测试，`S3CompatibleStore`使用Node内置fetch和AWS SigV4，无新增依赖。
- 服务启动时读取已完成的manifest；距上次小时备份满1小时或没有备份立即补做。进程内每分钟检查，小时档保留7天，日档按UTC自然日保留30天；同一次快照可上传两档。先上传数据库与图片，最后上传manifest作为完成标记，清理到期对象时先删除完成标记。
- 失败后分别等待1、5、30分钟重试，同一待上传快照保留原编号；四次仍失败后清理暂存并在下一小时尝试，错误日志不含密钥或远端返回正文。进程退出等待在途任务、清理暂存。
- `/health`的result含`backupConfigured`、`lastSuccessfulBackupAt`和`status`；未配置、尚无成功备份或超过2小时未成功时为`degraded`。生产监控需解析字段，不能仅依据HTTP 200判断备份健康；告警送达仍需部署验收。
- 通用环境变量：`BACKUP_STORE=local`或`s3`、`BACKUP_STAGING_PATH`。本地实现还需`BACKUP_LOCAL_DIRECTORY`。目录必须独立于源数据库与图片目录，不能放入项目公开静态目录。
- S3实现还需`BACKUP_S3_ENDPOINT`、`BACKUP_S3_BUCKET`、`BACKUP_S3_REGION`，可选`BACKUP_S3_PREFIX`；使用HTTPS、path-style兼容接口。`BACKUP_ACCESS_KEY_ID`、`BACKUP_SECRET_ACCESS_KEY`及可选`BACKUP_SESSION_TOKEN`仅由部署环境安全注入，不放命令参数、日志或文件；存储主体与最小权限由经营主体配置。

### 两种运行方式

优先让服务进程读取上述环境变量并自行调度。若使用系统任务调度器，任务在server目录每小时运行下面的publish命令，调度器禁止同任务并发，进程环境安全注入存储配置；程序自行判断小时/日档与保留期。两种方式选一种，避免两个独立进程同时发布。示例路径需要替换为已确认的源数据路径：

```powershell
node src/backup-cli.ts publish --database D:/hdm-data/mall.sqlite --uploads D:/hdm-data/uploads
```

任务最长时间需容纳1、5、30分钟重试，失败退出码非零；由系统任务监控失败并通知负责人，不把CLI成功等同于告警送达。未启用上传的手工create/verify/restore命令仍沿用下文，不自行轮转。

### 下载最新备份并隔离恢复

1. 保持运行数据不动，确认备份源可信并注入对应的存储环境变量。本地演练选择`BACKUP_STORE=local`和隔离对象目录；云端恢复选择已经授权的S3配置。
2. 准备存在且可写的隔离父目录，download和restore目标子目录必须尚不存在。执行：

```powershell
node src/backup-cli.ts download --out D:/hdm-recovery/downloaded
npm run backup:verify -- --from D:/hdm-recovery/downloaded
node src/backup-cli.ts restore --from D:/hdm-recovery/downloaded --out D:/hdm-recovery/restored
```

3. 下载器只选最新带manifest的完整快照，逐文件下载并核对哈希、完整性、业务关联；失败目录不视为可恢复备份，也不自动覆盖已有目录。恢复完成须有`restore-report.json`且issues为空，旧会话全部失效。
4. 在隔离服务核对订单、金额、库存、开票、隐藏评价、客服留言与照片权限，然后由负责人决定是否切换生产路径；本命令不切换正在运行的服务。

本轮证据：服务端check通过，常规及随机各300/300、0失败0跳过，含固定SigV4向量、S3分页编码与失败脱敏、小时/日档保留、重试与health降级、v16兼容及v17业务数据恢复。`_device_acceptance/step21/restore-proof-1794403667923/evidence.json`记录本地目录CLI发布713ms、下载267ms、恢复221ms，均退出0，43张表核对、issues=0；该CLI演练为无用户的种子数据，带开票、隐藏评价、留言及图片的数据由`service-backup.test.ts`另行验证。没有连接真实云对象存储，没有生产恢复或生产告警验收。

## 已实现的保证

数据库使用 SQLite 在线备份接口生成一致快照，包含尚在 WAL 日志中的已提交数据，不能用直接复制正在运行的 mall.sqlite 替代；快照转为独立数据库后，再从快照内账号资料读取头像引用并复制对应图片。

当前上传先写完整文件，再提交资料引用，文件名唯一且不会覆盖或删除，所以数据库快照中的头像能找到对应的完整文件；旧头像和未引用的文件不进入备份，生成商品占位图由服务代码提供；未来如果增加图片删除、商品上传或其他文件引用，必须先扩展备份收集规则和并发验证，再启用这些能力。

每份备份包含 mall.sqlite、uploads/、manifest.json，清单记录格式版本、数据库版本、创建时间、文件大小和 SHA256；校验会核对文件集合、哈希、数据库完整性、外键和头像引用，拒绝额外的 WAL 日志、重复清单项、越界路径及符号链接；清单最后生成，缺失清单或未通过校验的目录不属于有效备份。

恢复只写入全新目录，不覆盖正在运行的数据或原备份；复制后重新验证数据库，并删除全部会话，完成时写入 restore-report.json；恢复后必须重新登录，避免已退出的会话随历史快照复活；恢复报告生成前不得把该目录接入运行服务。

哈希用于发现损坏和复制不完整，不证明来源可信；备份含账号、交易、地址等数据，只从自己管理的备份源恢复，并由存储位置的权限和加密机制保护，Windows 目录权限按实际账户及 ACL 设置；本工具不自动上传、发送、删除或轮转备份。

## 操作命令

以下在 server 目录执行，每条独立运行；示例绝对路径须替换为实际数据和已有备份父目录，目标子目录必须不存在，备份不能放在源数据目录内。

```powershell
npm run backup -- --database D:/hdm-mall/server/data/mall.sqlite --uploads D:/hdm-mall/server/data/uploads --out D:/hdm-backups/backup-20261028-01
```

看到 `backup-verified` 才算创建并校验通过；复制到独立磁盘或受控存储后，在副本上再次执行：

```powershell
npm run backup:verify -- --from D:/hdm-backups/backup-20261028-01
```

恢复到新的隔离目录：

```powershell
npm run restore -- --from D:/hdm-backups/backup-20261028-01 --out D:/hdm-recovery/recovery-20261028-01
```

成功返回 `restored-to-new-directory`，报告位于目标目录的 restore-report.json；源数据库和上传目录不会被改写；失败退出码非零，可能保留不完整的目标目录用于排查，重试应选择新目录，不能把残留目录当成功产物。

## 故障恢复与复核顺序

1. 发生故障时先停止业务写入并保留原数据，记录故障时间和最后可用备份；不要在现有数据上试覆盖恢复。
2. 在新目录恢复并检查报告；沿用兼容的程序版本，设置 DATABASE_PATH 指向恢复目录的 mall.sqlite，UPLOADS_PATH 指向其 uploads，使用独立端口进行验证。
3. 检查登录、订单、库存、亲友权限和图片，核对备份创建后到故障之间可能缺失的业务；会话统一失效属于预期，用户需重新登录。
4. 当前版本 5 保存头像相对路径，服务端按 PUBLIC_URL 返回完整地址；版本 2～4 的本服务 UUID JPEG 历史地址在启动升级时转换。数据库与 uploads 一起恢复后，检查重新登录或读取资料得到的新地址及图片内容；客户端已缓存的旧完整地址需刷新资料。外部图片或不符合规则的历史地址不自动迁移，CDN 和网络入口仍须单独配置验证。
5. 对未付款订单，服务启动后的到期处理可能将其取消并归还库存，这是业务时间继续前进的结果；原始快照保持不动，核对时区分快照状态与启动后的业务变化。
6. 只有复核通过后才切换服务配置与入口，保留旧目录供回退；本轮没有执行真实环境停机、切换或部署，也没有开通自动备份任务。

真实支付和退款尚未接入，库存流水覆盖初始化、下单、取消、到期归还和人工调整；将来恢复不能仅依赖订单快照推断渠道是否已付款，须查询渠道并对账，完成期间应阻止重复履约；本轮未声称资金恢复已验收。

## 本次验证出的适用规则

SQLite 开启 WAL 时通过备份接口取得一致快照，再按快照引用复制不可变文件；不复制整个正在变化的目录来推断一致性；恢复清理历史会话并实际启动隔离服务验证业务，比仅检查数据库能打开更接近恢复目标；此规则只适用于当前文件先写入、引用后提交且不删除的上传机制。
