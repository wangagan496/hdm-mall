# 过期订单读检查验收

验收日期：2026-10-29。

## 目标

商品、购物车、订单详情和订单列表等读路径此前每次都会直接调用 `orders.expire()`。存在过期订单时，读请求会开启释放库存的写事务；连续读取还会重复做相同探测，增加 SQLite 写锁争用机会。

本轮保留写操作和定时任务的即时处理，并让读路径使用 `orders.expireIfDue()`：同一个服务实例内，连续 1 秒内的读请求合并为一次过期探测；超过间隔后再次检查。探测失败不推进时间戳，下一次读仍会重试。

## 代码变化

| 位置 | 变化 |
| --- | --- |
| `server/src/orders.ts` | 新增 1 秒读检查间隔和 `expireIfDue()`；详情、订单列表、亲友订单、结算预览改用合并检查；`expire()` 仍可由写操作和定时任务强制调用。 |
| `server/src/app.ts` | 分类、首页、商品、搜索、猜你喜欢、热门及购物车 GET 使用 `expireIfDue()`；购物车 POST 继续使用即时 `expire()`；定时任务继续每 30 秒调用 `expire()`。 |
| `server/test/optimization.test.ts` | 覆盖连续读只探测一次、首次读处理过期订单并归还库存、写操作不受读间隔节流，以及商品和购物车真实 GET 路由的首次读取。 |

## 验证结果

专项测试“订单读请求合并过期探测，首次读仍处理过期单且写请求强制检查”通过：首次读将过期订单改为已取消并归还 1 件库存，紧接的第二次读不再重复探测；随后把另一订单设为过期，写入口仍立即探测并拒绝已过期订单。

完整基线 `pwsh -File scripts/verify-enterprise-baseline.ps1` 通过：服务端 TypeScript 检查、69 项服务端测试和 82 项客户端检查全部通过，0 失败、0 跳过，共 151 项。该检查未测量生产响应耗时、并发容量或 SQLite 锁等待比例。

## 边界

1 秒是读检查合并窗口，不是订单过期时间；写操作、定时任务和显式 `expire()` 不等待该窗口。服务重启后时间戳重新开始，过期订单仍会在下一次读或定时任务中处理。本轮未决定替换 SQLite，也未部署、迁移开发数据或接入真实支付。
