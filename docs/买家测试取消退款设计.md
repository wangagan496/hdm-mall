## 二、数据结构与备份（迁移 008，数据库版本 7 → 8）

### 2.1 存储选择

拟新增 `order_cancel_requests`（每次明确申请一条，保留历史）和 `order_cancel_actions`（成功操作及请求号回执）。不在订单里堆叠当前状态、原因、次数，不增加订单状态数字，`orders.state` 仍为 1 至 6。

一次申请可以撤回后再申请，商家旧页面必须指向它看到的那一次申请，不能误处理新申请；只覆盖订单字段无法可靠保存这一关系及幂等历史。两张表只服务本流程，不引入通用工作流。

| `order_cancel_requests` 字段 | 含义与约束 |
| --- | --- |
| `id` | 服务端 UUID，撤回、处理必须携带此申请号 |
| `order_id` | 订单外键，不级联删除历史 |
| `sequence` | 同订单从 1 递增，事务内分配，`UNIQUE(order_id, sequence)`；避免同毫秒多次申请排序不确定，不是可用次数额度 |
| `requested_by` | 会话用户，必须是订单 `owner_id` |
| `payment_id` | 申请时锁定的有效支付外键；金额、付款人、时间取该支付，不接受客户端指定退款人或金额 |
| `state` | `pending` / `withdrawn` / `approved` / `rejected-shipped` / `auto-approved` |
| `created`、`deadline_at` | 注入时钟毫秒时间；截止 = 创建 + 259200000 毫秒（72 小时，不是第三个自然日） |
| `resolved_at` | pending 为空，其他状态必填 |
| `resolved_by` | 撤回填下单人，商家处理填商家，自动同意为空；不能客户端自报 |
| `reject_reason` | 仅拒绝并发货必填，trim 后 1 至 200 字，允许“已打包”“已交物流”；不沿用核实付款的 5 字下限 |
| `refund_id` | 仅人工/自动同意非空，外键指向本次退款；撤回、拒绝为空 |

约束：`UNIQUE(order_id) WHERE state='pending'`；到期扫描索引 `(state, deadline_at, id)`；最新记录按 sequence 取。CHECK 限制状态、截止及终态字段组合；跨表订单/支付关系在事务校验。历史记录不删除，不重新变成 pending。

| `order_cancel_actions` 字段 | 含义与约束 |
| --- | --- |
| `id` | 操作回执 UUID |
| `order_id`、`cancel_request_id` | 订单与申请外键 |
| `actor_id` | 会话操作者；自动同意为空 |
| `action` | `request` / `withdraw` / `approve` / `reject-and-ship` / `auto-approve` |
| `request_key` | 全表唯一；用户为 UUID，自动任务为 `auto-approve:<申请号>` |
| `request_body` | 规范化目标、动作、原因，用于比较同号异参，不存 token |
| `result` | JSON 成功回执，只存目标号、动作、当时生效状态、时间、退款号，不存完整订单或地址 |
| `created` | 注入时钟的完成时间 |

申请、订单、库存、退款、通知和成功回执一起提交或回滚。只记录成功回执，拒绝请求不占号。全局号碰撞返回通用冲突，不泄露其他账号目标；查询按操作者及当前权限过滤。

### 2.2 支付、退款与通知

- 有效支付沿用现有认定并核对金额：`succeeded`、匹配 `orders.paid_by/paid_at`、金额等于订单、尚无退款。申请/同意/拒绝发货/普通发货均在事务复核；申请固定 payment_id，不重新挑选付款人。
- 2026-11-06修订：退款原因复用 `cancelled`，通过 `order_cancel_requests.refund_id` 区分本步与确认中取消退款；不新增原因，保留每支付最多一条退款约束。
- 退款后不清 `paid_by/paid_at`，保留付款历史及亲友可见性；不能因有效支付已退款而重新开放付款。
- `Payments.createRefund` 当前私有。拟提供窄接口 `createOrderCancellationRefund(orderId, paymentId, now)`，事务内复核并调用原 `createRefund`，不另开事务、不调渠道；Orders 管理外层事务，不复制退款 SQL、通知和重试策略。
- 同意只为锁定的有效支付创建一条本步退款；订单已有 duplicate 等退款继续各自处理。“一条退款”指有效支付，不限制整个订单所有退款总数。
- 复用 `createRefundNotices`：下单人、该笔付款人各一条，同一人去重；申请、撤回、拒绝不伪装成退款通知，不新增通知种类。

### 2.4 备份统计与恢复校验

`backup.ts` 的 manifest 版本枚举、检查逻辑、返回类型均接受 8，备份格式仍为 1；原版本 2 至 7 备份仍能验证与恢复，恢复到新应用后再升级。

统计清单保留原表；版本 ≥ 7 补齐 `payment_notices`、`payment_review_resolutions` 行数，继续统计 payments、refunds、refund_retry_actions；版本 ≥ 8 增加取消两表。数据库快照包含全部表，行数用于核对历史未丢失，不代替业务校验。

当前 payment-mismatch 对所有 paid_by 非空订单要求恰好一笔“尚无退款的有效支付”，会把本步合法已取消订单报错。拟按状态细化，不能简单排除全部已取消订单：

| 状态 | 校验 |
| --- | --- |
| 待发货/待收货/待评价/已完成且 paid_by 非空 | 恰好一笔有效支付；pending 申请必须指向这笔 |
| 本步已取消且有同意终态申请 | 付款历史匹配；申请退款对应锁定 payment、全额、原付款人、原因 cancelled；不得存在 shipped_at 或该有效支付仍无退款 |
| 其他已取消历史订单 | 检查原支付/退款关系，不伪造同意历史、不全部放行 |
| 申请及回执 | pending 至多一条且订单待发货；withdrawn 无本次退款；拒绝终态有原因且已发货；同意终态有正确退款；回执目标和操作者合法 |

拟增加 `cancel-request-mismatch` 备份问题项及 schema。恢复后补扫已到期 pending；已同意只继续原退款，不再释放。验收 integrity_check、foreign_key_check、行数、回执、通知已读状态、库存流水、退款归属，保留原恢复清会话行为。

## 三、状态、权限与并发裁决

### 3.1 状态和能做什么

“取消申请审核中”是待发货的取消子状态，不是新履约状态；继续在买家待发货及商家发货列表出现，但不能绕过申请发货。

| 当前状态 | 下单人 | 付款亲友 | 商家 | 库存/退款 |
| --- | --- | --- | --- | --- |
| 待付款、确认中/核实中（1） | 原取消和付款规则 | 原代付权限；不能取消 | 不可发货 | 原取消释放一次，迟到成功原机制退款 |
| 已付款待发货，无 pending（2） | 取消订单弹申请确认；提醒发货 | 查看自己付款，不可申请/撤回 | 确认发货 | 保持占用，无本步退款 |
| pending，未到截止（2） | 看审核中、撤回；无重复申请/提醒发货 | 只读审核中 | 只能处理申请：同意或填原因拒绝并发货 | 保持占用，不退款 |
| 已撤回（2） | 回待发货，可再明确申请 | 查看待发货 | 普通发货 | 不释放、不退款 |
| 人工/自动同意（6） | 查看退款 | 查看本人付款/退款 | 从发货列表移除，禁止发货；转人工可在原核实列表重试 | 释放一次，建有效支付退款 |
| 拒绝并发货（3） | 看原因及“如有问题请联系客服”；原确认收货，不可取消 | 看权限内信息，原仍绑定亲友代收规则不变 | 移出发货列表，不可再处理 | 不释放，无取消退款 |
| 普通已发货及后续（3/4/5） | 不可取消，原收货/评价 | 不新增权限 | 不可再次发货或取消退款 | 不因申请变动 |

服务端以 owner_id 而非 paid_by/受邀关系决定申请和撤回权限。实际付款亲友也不能申请；解绑不影响查看自己的付款退款，不因此获得地址或他人支付信息。

### 3.2 六类动作

| 动作 | 事务内前置条件 | 成功结果 |
| --- | --- | --- |
| 申请 | 下单人；state=2；有效支付；无 pending；请求号未使用 | 新 pending 与回执，截止本次创建 +72小时，订单仍2，不退款不释放 |
| 撤回 | 下单人；指定申请 pending、订单2；未到72小时硬截止 | withdrawn 与回执，订单仍2，不影响再申请资格 |
| 同意 | 商家；指定申请 pending、订单2、有效支付仍为申请那笔 | approved、订单2→6、释放一次、退款及通知、关联退款与回执 |
| 拒绝并发货 | 商家；指定申请 pending、订单2、有效支付有效、原因合规 | rejected-shipped、原因及处理人、订单2→3和 shipped_at、回执；不退款不释放 |
| 自动同意 | 指定申请 pending、订单2、注入时间达到截止 | 共用同意事务，auto-approved、处理人空、固定自动操作键 |
| 普通发货 | 商家；订单2；无 pending；有效支付 | 原接口2→3；有申请拒绝，已取消专用提示 |

申请不是已取消，同意只是退款发起，渠道成功才是已退款。退款失败不恢复订单、不重新占库、不开放发货。拒绝与发货不可拆开，不存在“拒绝但仍待发货可再申请”的中间态。

同单可以有多个历史撤回，每次新申请新号。撤回不消耗再申请机会，不设计“被拒后再申请一次”；Q1已确认不设业务次数上限，现有接口限流不等于次数额度。

### 3.3 事务与库存边界

用现有同步 `Database.transaction`（BEGIN IMMEDIATE）串行裁决，事务内重读订单、指定申请、有效支付、成功回执；不以事务外 hasPending、UI 缓存作最终判断。申请条件更新、订单条件更新、库存、退款、通知、回执一起提交，检查更新行数；失败全部回滚。各动作进入同一事务域，不是把多个 HTTP 请求包在一个长事务。

现有 Orders.cancelAndRestoreStock 和 Payments.releaseStock 仅支持 state=1，不能直接用于本步。拟在 Orders 内增加专用于2→6的同意流程，人工与自动共用；先条件更新确认唯一胜者，再逐 SKU 加回及记流水。人工同意用原 cancel 类型及商家 actor，自动用原 expire 类型及空 actor，具体原因由申请记录表达，不新增库存类型。

继续依赖 inventory_one_release 对同单同 SKU 的唯一释放约束；库存失败或流水冲突必须回滚，不能吞掉唯一键异常后提交库存加回。按原订单数量释放，与申请次数无关。

渠道查单/退款异步调用在事务外，任何 await 不跨同步事务，不嵌套 transaction。支付结果落库时再读订单，不能用调用渠道前的快照恢复待发货。

### 3.4 并发矩阵（B-63）

| 同时到达 | 裁决 | 不变量 |
| --- | --- | --- |
| 申请 vs 普通发货 | 申请先：发货提示“买家已申请取消，请先处理取消申请”；发货先：申请提示“已发货，请联系售后” | 不直接退款，不同时审核中又发货 |
| 撤回 vs 同意 | 撤回先：同意失败；同意先：撤回失败并刷新已取消 | 单一申请终态，至多一笔取消退款和一次释放 |
| 撤回 vs 拒绝并发货 | 撤回先：旧申请不能拒绝发货；拒绝先：撤回失败 | 旧商家页面不能处理后来的新申请 |
| 同意 vs 拒绝并发货 | 先成功一方生效，另一方明确终态冲突 | 有效支付不既发货又取消退款 |
| 自动同意 vs 人工同意/拒绝/撤回 | 到期前正常先后，到期边界依 Q2已定先自动同意 | 一个终态、一次自动动作 |
| 普通发货 vs 申请处理 | 看到 pending 即拒绝；撤回先完成可正常发货，同意后拒绝 | 不能靠直接发货抢掉 pending |
| 双申请/同号重试 | 同号同参回原回执，不同号遇 pending 返回409 | 唯一 pending，旧号不因已撤回而新建 |
| 多商家/重复扫描/重启 | 条件更新、唯一键与回执裁决，不依赖进程锁 | 不重复发货、退款、释放 |
| 旧撤回/旧处理 vs 新一轮申请 | 必须匹配原申请号，不盲写最新申请 | 新申请及其截止不受旧操作影响 |

“不既发货又退款”限定本单有效支付的取消退款；原 duplicate 多扣退款可以与正常发货并存，不能把 B-57 判错。

### 3.5 与支付确认的边界

旧 `PUT /member/order/:id/cancel` 仅保留待付款/确认中取消，不扩展成已付款申请；新申请走新路径。已取消重复旧取消仍可返回现状，不产生申请。

确认中取消先落库：仍立即取消、关闭原 pending、释放一次，之后成功用原 cancelled 原因退款。新申请先于支付确认：因尚未待发货而被拒，不排队；刷新并再次确认后才能申请。

支付成功先落库、旧取消随后到达：现有代码拒绝，不自动退款；原方案第三节“两种结果买家都拿回钱”与工作区及新口径冲突。Q3已定保留现有拒绝语义，刷新后弹新的申请确认，由用户明确提交；不能无提示把旧“立即取消”意图转为商家审核。本轮同步方案竞态描述并测试两种先后顺序，旧取消接口语义保持不变。

申请期间同笔成功回调不改变申请；其他支付迟到成功仍按原规则作多扣/已取消退款，不替换锁定支付。支付与取消同用数据库事务机制，网络返回后用最新状态裁决。

### 3.6 72 小时任务与退款驱动

在 app.ts 现有30秒 timer 中保留 orders.expire，再调用拟新增同步 `orders.processDueCancelRequests(clock.now())`，之后运行原 payments.reconcile；不新增定时器。单个异常申请记录错误、允许其他到期申请继续，下一轮重试。

逐单事务内重读 pending、订单、截止、有效支付；提交后才由 reconcile 调渠道。提交前退出则回滚，提交后未调渠道则下次继续同一退款单。启动可补扫一次；正常服务首个到期扫描约在边界后0至30秒，停机/故障不承诺此延迟。

4a采用事务内创建退款单入队、原30秒timer驱动payments.reconcile的方式；同意接口返回不等待渠道。渠道失败只影响退款，不回滚已同意或假报已退款；GET不调用渠道、不承诺同步退款。

Q2已定硬截止：事务中 now >= deadline_at，先走自动同意提交，再在事务外返回迟到操作的冲突；不能在同一事务中抛冲突把自动同意回滚。撤回、商家处理、普通发货等写入口在扫描前也执行此裁决。只读页面尚为 pending 时显示“已到自动处理时间，正在处理”，不自行变为已取消。

退款重试沿用第二步：1、5、30分钟、之后每小时；自退款创建满24小时未成功则转人工、停止自动重试、生成原 review 提醒，商家重试原单。72小时从申请创建算，24小时从退款创建算；所有业务时间来自注入 Clock。

### 4.2 请求号与恢复

1. 用户确认时生成 UUID，把账号、订单、申请号、动作、规范化体先持久化再发送；持久化失败不发送。同一未决动作超时、杀进程、同账号重新登录均复用原号。
2. 服务端事务中先验身份目标，再查成功回执；同号同参同操作者返回原回执，不因当前已终态失效；同号异参/目标冲突，不执行。不同号不能绕过 pending/终态。
3. 网络异常不显示成功或创建第二申请；恢复先查回执，404 才按原号原参重发并刷新。查询与重发间原请求刚完成，也由同号兜底；永久4xx不无限重试。
4. 撤回成功后，只有再次明确确认申请才换号。迟到响应检查账号/token、页面代次、目标申请号，再刷新；不得覆盖新一轮申请。
5. 原 OrderCancellation 只存待付款取消意图，成功条件是 state=6，不能直接复用执行申请。拟单独增加薄的申请动作恢复封装给列表、详情、商家卡片共用，持久化命名空间与旧意图分开；不重写旧取消模块。

> 取消申请提交后，商家同意即不再发货，¥金额将原路退回付款账户。确定申请取消吗？

“全部”原位保留买家取消单；待发货栏目保留 pending、同意后移除；普通发货/拒绝发货后进入待收货。商家仍按 state=2 原顺序分页。亲友 listFilter 保留本人存在 payments 记录的已取消订单，包含原失败支付可见规则；仅受邀未付款者不增加权限。

复用进入页面、回前台、手动刷新、操作后刷新，不新增72小时长轮询。页面不靠倒计时自行取消，也不靠手机系统日期决定最终权限。

### 5.2 退款原文与逐笔权限

直接使用 payments.orderFields 的 paymentNotice，不在三个页面另造不同文案：

| 状态 | 原文 |
| --- | --- |
| 退款中/自动重试 | “¥金额（时间 由 xxx 付款）正在退回付款账户。退款处理中，系统会自动重试，无需操作。” |
| 成功 | “¥金额（时间 由 xxx 付款）已原路退回付款账户。” |
| 人工 | “¥金额（时间 由 xxx 付款）退款遇到问题，我们正在人工处理。可以进入帮助与客服咨询。” |

时间取原 channel_paid_at，保持上海时区格式，金额按分转元。下单人看本单全部退款，付款亲友只看本人支付退款。仅参与其他支付、不是有效付款人的 paymentOnly 投影仍 skus为空，不增加地址、拒绝原因、申请操作记录或他人退款，不能因共享展示绕过原提前返回分支。

### 5.3 红点

- 同意创建退款时沿用 payment_notices，通知下单人及该笔付款人，同一人去重；重试、重复同意、扫描不重复创建 refund 提醒。
- 24小时转人工按原机制增加 review 提醒。现有 finishRefund 成功只更新状态，不新增成功通知，本步不擅自加“成功再亮一次”；旧提醒未读则继续亮，详情呈现最新退款状态。
- 买家、亲友分别打开授权详情，只清本人该单提醒；列表、动作回执、商家处理不代为已读。返回列表、“我的”、亲友中心按原机制刷新，一方查看不能替另一方消点。
- 申请、撤回、拒绝只改文字按钮，不新造 payment_notices；商家知情靠列表标注和服务端硬拦截，不承诺新推送/商家红点。

## 六、订单展示字段增量

Orders.present 合并取消投影，Payments.orderFields 保持支付退款投影。服务端计算能力；新字段缺失默认不能执行新动作，不误把老服务端响应当作授权。

| 字段 | 拟定含义与可见范围 |
| --- | --- |
| `cancelRequest` | 无申请为null，否则最新sequence摘要 `{ id, sequence, state, createdAt, deadlineAt, resolvedAt, rejectReason, refundId }`；下单人、完整可读有效付款亲友可见，商家原发货列表可见pending，不返回操作者内部ID或全量历史 |
| `canRequestCancel` | 下单人、state=2、无pending、有效支付；撤回不扣资格；Q1不限次数 |
| `canWithdrawCancel` | 下单人、state=2、最新pending；Q2已定还要求未到截止 |
