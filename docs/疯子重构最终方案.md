# 惠多美疯子重构最终方案

本文是后续实施的总入口。付款只用支付宝沙箱；本文件中的目标、目录和验收均为待实施方案，不代表本轮已运行。四份原文保留背景、证据与细节，最终决定以本页及本文路线为准。技术报告以 B30BD45A 开头的版本为输入，包含延迟 Teleport 的补充。

## 开头一页：让商城长出能力

为什么这样排：先让买家下单前看清价格和承诺，收货后能逐条核对，降价能申请补差，有争议能举证申诉。服饰、鞋靴先把尺码与版型说清，评价和退货分清尺码不合还是质量问题；价保之后紧接本人可设的花钱刹车，先让人决定什么时候别买，再接后面的持续自动办事。商家先确认自己承诺了什么、最多承担多少责任，再发布政策和处理争议。每完成一阶段都保住前面已经能用的商城，中途停下也能解决实际问题。来源核查和可信评价接在承诺之后，退货成本与逐项验收接在人工案件之后；预售进度、能一步找人工的事实客服、回款解释和促销试算也先交可用入口。模块安装、合体动画、进程治理和多端技术随后叠上，仍按原定范围交付，不让用户等这些展示做完才用上核心能力。

我要做的商城，用户可以亲手拆开，也可以装成自己需要的样子。手机模块舱装上商品对比后，首页长出入口；AI按一句需求组合商品、报价和退货条件，拼出可操作的页面。商家选装店铺能力，买家调整自己的首页。后台模块能真实停进程、换版本、接回，组合图跟着事实变化。AI是默认入口，用户决定自主程度；付款和不可逆操作由本人确认。同一内核还要接入栖居管家和题海方舟，各自保留账号和数据库。解体、升级、合体都要拿真实状态和运行证据证明。

30秒讲稿，只有实现并验证后才能作为成果说：“我把商城做成可现场拼装的应用：手机按需安装模块，首页长出入口；AI组合商品、报价和退货能力，生成可用对比页；后台推荐模块能停进程、切版本，旧订单的承诺仍有效。同一套内核也能接物业和学习项目，三个项目的数据各自独立。”

下面的“架构”“技术”“回归”“追踪”分别指《疯子架构设计方案》《疯子重构技术进化分析》《疯子回归提案》《链路追踪工具选型》，都在本目录。“方向调研”指《惠多美方向调研》，“补充调研”指《网购痛点补充调研》；章节号沿各自标题。用户最终决定覆盖原文中的待定、推荐或较早范围，当前共39项决定（D1–D22、R1–R7、T1–T10）；本轮仅在D9、D13、D14、D15、D19、D20原结论后各补一句，并新增D22，其余原有决定行逐字保留。视频评论只作用户选择的参考，网友自述未经核实，不作为平台事实或本项目业务效果的证明。

  └─ ArkWeb打包H5确认页，受限桥、本人确认             │
App内商家端 ─ 商品与承诺确认 / 案件 / 规则 ───────────┤
独立React商家后台 ─ 守护编排、案桌、装配、版本台 ────┤
后补独立Vue买家Web ─ 配方、首页装配、动态模块 ───────┤
                                                       ▼
              鉴权与能力网关 ── SSE任务事件 / WS客服
                │                     │
                ├─ AI驾驶员：双模型→受限意图/配方→权限与等级校验
                │  └─ 固定意图兜底；确认凭据由本人取得，支付凭证不交AI
                ├─ 交易核心：报价、订单、库存、资金与回执同库同事务
                │  └─ 支付宝沙箱等外部网络在事务外，以幂等与回执协调
                ├─ 可信模块进程：推荐、纯试算等；注册/健康、配置版本、灰度、排空
                └─ 承诺快照、证据、案件、补差记录和审计：已有义务独立保存
                         │
              共用内核：Node运行包 / ArkTS HAR / Dart适配
              契约、依赖图、配方校验、生命周期、动作回执
                         ├─ 惠多美自己的账号和数据库
                         ├─ 栖居管家自己的账号和数据库：只读维修预览
                         └─ 题海方舟自己的账号和数据库：本人学习摘要只读

各端 traceparent → 网关/核心/模块进程 OTel → 精简Collector → Jaeger 2
Web脱敏会话 → rrweb回放；故障开关控制演示，后续加Toxiproxy。

已有：原生商城、内嵌资料H5、Fastify和SQLite事务，以及历史沙箱链路证据；不能当作本方案已实现。新增：来源核验、承诺评价、退货成本与验收、预售时间线、事实客服、回款投影、促销试算，以及内核、模块舱、驾驶员、配方、独立后台、治理和追踪。补充业务共享原承诺、订单、案件和资金记录，AI事实客服只接纯读投影；这些均为计划，不表示已经实现。待验证：真实后装、跨端行为、模型效果、设备与分发条件。能力图和动画只能反映真实状态，失败保留手动入口。

## 实施路线：先解决网购痛点，再让商城真正变形

以下是后续实施顺序，不是本轮操作记录。阶段0保住现有商城，阶段1交精确报价；阶段2交承诺与来源，阶段3交可信评价，阶段4交价保，阶段6交人工举证申诉与仅退款保护，阶段7交退货成本和验收，阶段8交预售时间线，阶段9交事实客服，阶段10交回款看板，阶段11交自家促销试算；阶段12起再叠真实HSP、进程、AI配方、多端、治理与实验。无论做到哪一阶段停下，手上都应是一个真正解决网购痛点、买家和商家能用的商城；每阶段保住前一阶段可用入口和旧义务，不为后面的展示推倒重来。依赖更新与功能迁移分开验证，U0–U7保持技术10.7的原组顺序与组内约束；不需要新基础设施的业务先沿现有栈跑通。所有新增目录均为拟定目录，不把现在不存在的包写成已有。

完成条件与验证：每条正式承诺有来源、商家逐条确认和订单冻结版本，改商品不改旧单；买家从订单逐条核对并把不符项及其冻结引用带入售后。服务端验证恶意资料、越权、草稿过期、重复发布、模型失败与预算上限、下单并发和备份恢复；设备走抽取、逐条确认、发布、下单、核对和现有售后入口。抽取成功、内容正确和商家采纳分别报告；单模型跑通不等于D1双模型已完成，全品类覆盖仍需完整清单与边界样本。

文件与新增内容：继续改商品维护、订单详情、S/src/products.ts及阶段2承诺端口；新增S/src/source-verification和contract-kit/v1/source-records，复用受限上传并增加资料版本、批次关联及核验记录。AI从这些原始材料抽承诺，仍走D13商家逐条确认；未知、过期、批次不匹配必须明示，AI不授予核验通过。原件按角色受限，买家查看可公开的脱敏版本与来源摘要，不把私人授权附件全部公开；下单冻结引用，材料更新不覆盖旧单。

补充完成条件与验证：每条来源承诺可追到下单时的材料及当时核验状态，当前撤销/失效另显提示；服务端核附件归属、批次/版本错配、失效时间、重复提交及备份恢复，设备只走上传、抽取、逐条确认、查看来源与核验说明。真实权威核验渠道未接入就保持待核验，不能靠AI补结论；为控制阶段大小，逐条评价与异常复核独立放到紧接的阶段3。

服饰、鞋靴的尺码版型补充：对谁有用是买家和商家，现有服饰、箱包、鞋靴中，服饰与鞋靴先用上这项能力，箱包不硬套鞋服版型。用户可见的是尺码表与“偏大 / 偏小 / 标准”版型并列；买家收货逐条核对时可直接选“尺码与承诺不符”，带着原承诺进入售后。没有资料依据就显示未知，不能凭品牌或AI猜版型。

尺码改动与新增：在本阶段商品详情、商品维护、承诺字段规范和受限契约中补尺码表、版型、适用品类与来源；AI从商品详情抽取，商家逐条确认后发布，沿原承诺链冻结到订单与SKU版本，不另开结构化手填承诺入口。版型修改重新抽取确认，不覆盖旧订单；“个人穿着不合适”和“尺码与承诺不符”分开记录。

尺码完成条件与验证：正式版型能追到详情依据、AI抽取与商家确认，买家能从收货核对一键选中不符项。服务端核品类适用、来源缺失标未知、资料变化旧草稿失效、确认与旧单快照隔离；设备只走查看尺码版型、逐条确认、收货核对和原售后入口，不替服务端制造越权或版本篡改路径。

### 阶段3：收货后逐条评价承诺，异常由人工复核

对谁有用：买家 / 商家；买家看同SKU承诺是否兑现，商家能对不实评价说明理由。

用户可见：仅本人真实收货的订单项可评价，按下单承诺逐条打分并附说明；其他买家看对应SKU和承诺版本的汇总，商家可公开回复或申请复核，评价者可补充事实。评价者的联系方式不向商家提供，商家不能因为差评找上门，不能打电话、发短信或私信索要删改；改不改评价只能由买家本人主动决定，商家要沟通只能通过站内公开回复或售后案件。每条评价标明对应的下单承诺快照和SKU版本，换链接、改商品、下架后重新上架都不能沿用旧评价；历史评价仍可查看原版本。每条评价按实际依据显示“已真实收货”“对照承诺逐条打分”等可验证标记，无法验证的内容明确区分，不能宣称有标记就一定不是刷单。商家认为遇到恶意差评时，阶段3先登记，阶段6接入申诉，届时走已有举证申诉流程，由处理员按证据处理；商家不能直接删评，也不能用补偿换删评。异常只标待复核，不凭低分、正常退货或AI风险分直接删评、判恶意或限制售后；真实订单关联也不宣传为绝无刷单。

用户可见补充：评价同时让人看清“出了什么问题”和“商家怎么处理的”，商家补偿后原问题和原评价仍在页面上，买家可以追加“处理后感受”，处理得好也能被后来的人看见。处理记录由系统从售后案件关联，不能由商家自己写；阶段3先预留关联位，阶段6案件上线后接入，接入前不展示虚构的处理记录。只要本人真实收货过，在评价时限内退款、关单后照样能评价，时限从签收算起；没有收货的仅退款订单不进入商品收货评价，页面单独说明适用规则和不能评价的原因。匿名不只隐藏联系方式，还模糊精确下单时间、少见规格组合、收货地区等能倒推出订单的细节；销量很少时延迟或汇总展示，避免商家凭“最近只卖一单”认出评价者。评分分商品、物流、售后三项，逐条承诺打分归入商品，物流慢不拖累商品分；未发生售后时明确显示未发生，不强迫打分，中评作为正常评价展示，不归作差评。

改现有文件：订单详情、既有评价入口、商品详情、传输模型及S/src/orders.ts的收货资格只读接口；既有评价实现文件在开工时按真实入口定位，不新造第二套评价。新增：S/src/review-verification、contract-kit/v1/promise-reviews及下一号迁移，订单项与承诺快照引用、逐条评分、商家回复和人工复核记录，App内复核入口。评价固定关联订单项、下单承诺快照和SKU版本，展示与汇总按原版本取数，换链、改商品或下架重上均不得迁移旧评价或继承其汇总。补可验证标记及其依据引用，缺依据不打标；评价、回复和案件传输字段不暴露评价者联系方式，并核对商家可访问的关联订单字段，不能从评价反查联系方式。只向买家本人开放主动改评入口并保留原文和修改记录，商家无删改权限，回复或售后处理不得把补偿与删评挂钩。补恶意差评登记、证据和进度字段，阶段3先登记，阶段6接入申诉，关联已有案件与处理员权限，不提前另造申诉裁决流程。

改动与新增补充：保留原问题、原评价与买家追加感受，不能用退款、补偿或处理结果覆盖原文；售后处理记录阶段3先预留关联位，阶段6接入案件记录，由系统读取实际处理事实，商家公开回复不能冒充系统处理记录。评价资格依据本人真实收货历史和从签收起算的评价时限，不因退款、关单撤销；签收时间只用于时限起算，不替代本人收货确认，缺少可信签收时间时明示待核实，不编造时间。未收货仅退款沿用无收货不得评价的边界，单独返回规则说明。服务端统一模糊可反推订单的字段，覆盖评价、回复、版本与案件关联展示；原订单、SKU版本和承诺快照仍保留内部准确绑定，不能为匿名串用不同版本的评分。增加低销量评价的延迟或汇总展示规则，延迟期间保留原评价和提交记录；商品、物流、售后分开存储与汇总，逐条承诺评分纳入商品维度，中评独立正常展示，不归入差评。

新内容与边界：收货资格使用核心已确认记录和本人收货动作，快递鸟签收提示不能自动代收货；沿用现有售后可能触发的本人收货确认并明示含义。无收货记录不得评价，旧单无承诺快照则只保留原普通评价，不补写逐条得分。人工复核需独立授权、理由和原文留痕，双方看到结论并可请求更正；阶段6案件入口就绪后关联申诉。可选AI只整理异常线索，不替人判刷单或恶意差评。

依赖：沿U2基线，无需HSP、React或SSE；沿用阶段2身份、附件、版本和模型预算边界；售后处理记录依赖阶段6案件，阶段3先预留关联位，阶段6接入。

完成条件与验证：每条新评分可回到真实收货订单项、下单承诺快照和SKU版本，页面能看清对应版本与标记依据，无法验证的内容单列且不宣传绝无刷单；商家拿不到评价者联系方式，只有买家本人能主动改评，商家沟通只走公开回复或售后案件，不得直接删评或用补偿换删评。服务端验证未收货/越权评价拒绝、重复提交、跨SKU汇总隔离、版本与复核权限，并验证越权获取联系方式（含从评价关联订单反查）、商家删改评价、换链/改商品/下架重上沿用旧评价或汇总均被拒绝，缺依据不能打可验证标记。设备只走真实用户能点的本人收货、逐条评价、查看版本和标记、本人主动改评、商家公开回复或售后沟通、登记恶意差评、人工复核和查看更正；越权和换链沿用等拒绝场景留在服务端验证，不造设备操作入口。恶意差评阶段3先登记，阶段6接入申诉：本阶段核登记内容和进度，不能算申诉已完成，阶段6再沿已有举证申诉入口验证处理员按证据处理、双方查看理由；不以删评作为补偿发放条件。演示合成订单明示来源，不拿模拟收货证明现实签收。
完成条件与验证补充：服务端验证真实收货后退款、关单仍可在时限内评价，时限从签收起算且签收不自动取得评价资格，未收货仅退款被拒绝并有单独规则说明；验证精确下单时间、少见规格组合、收货地区及关联订单、版本、回复和案件字段不泄露可识别评价者的信息，低销量延迟或汇总规则生效且不能绕过提前读取，原评价仍保留。服务端分别验证商品、物流、售后评分与汇总互不混用，逐条承诺评分归商品，物流低分不改变商品分，中评正常展示且不归入差评。阶段3核对售后关联位、原评价保留和买家追加感受，不把关联位算作案件接入；阶段6接入后再验证处理记录来自系统关联的真实案件、商家不能自行填写，补偿或案件关闭后原问题仍展示。设备只走真实用户能点的退款或关单后评价、分维度打分、查看中评与匿名展示、追加处理后感受；阶段6再走查看原问题和系统处理记录的路径。退款后资格边界、信息不外泄、延迟或汇总触发与绕过等留在服务端测，不为设备验收增加调时钟、改销量或越权入口。

尺码评价补充：对谁有用是后来选尺码的买家，以及想改版型的商家；用户在商品分维度打分里回答“尺码合不合适”，可反馈偏大、偏小或合适，有实际依据时再补偏差幅度。后来买家看到对应SKU和承诺版本的汇总，例如数据确实支持时才显示“多数人说偏大半码”，样本不足显示暂不足以判断，不把示例写成真实统计。

尺码评价改动与新增：扩展本阶段评价入口、商品详情、S/src/review-verification和promise-reviews契约，增加尺码适配反馈及汇总；复用商品评分和版本关联，不混入物流、售后分数，不从个人穿着感受直接推断商家违约。低销量按D15既有匿名规则延迟或合并显示，合并仍限同一SKU与承诺版本，不能为凑样本串用旧版或不同商品。

尺码评价完成条件与验证：服务端验证尺码汇总的收货资格、版本隔离、偏差幅度依据、匿名字段、低销量延迟或合并及其绕过请求；原始反馈和准确版本引用保留，公开接口不能提前读出匿名受保护样本。设备只走评价中选择尺码合适程度、查看汇总和匿名提示；不加改销量、调阈值或读原始评价的设备探针。需要多少条评价才可信，待实施时根据数据决定。

### 阶段4：规则有预告，价保有额度，降价可确认补差

对谁有用：买家 / 商家；买家不用反复盯价和重填补差申请，商家先看清责任上限再发布承诺。

用户可见：买家看到新旧规则及生效点、保价不保库存、订单自己的价保期限与剩余额度；降价雷达发现符合条件的整篮新低，自动生成补差单草稿，买家一键确认后由原核心执行。商家在App内预览最坏赔付、核对预算后本人发布政策；双方可查看同一笔补差的计算依据与只读回放，旧单仍按旧版。

改现有文件：S/src/promotions.ts、orders.ts、payments.ts、after-sales.ts、reconciliation.ts及价格/退款备份校验；结算、商品维护、订单详情和App内商家政策页。新增：S/src/protection、price-events、price-radar、compensation、只读replay与下一号迁移，App内补差确认和回放页；D10的guard-recipes与React守护编排台留阶段16。

新特性：先用批准的确定性政策配置跑通D6的A/B/C叠加、D12降价雷达与补差回放，回放和影子对照只读，绝不二次发退款。价格/促销/库存可售与购买条件事件、政策/计算器版本、服务端时间及observedAt/effectiveAt分开保存；回放页先按已存版本解释同一笔补差，阶段16再接AI配方编排。对账和资金不让AI猜。

最小跑通办法：App内商家页配置已批准政策、试算最坏额外让利并本人发布；买家从订单手动刷新读取预告、领取结果、补差草稿和回放，不等React、SSE或AI守护编排台。雷达用服务端确定性价格事件和持久化调度/检查点，重复或重启仍按同一订单、政策版本和降价事件幂等生成草稿；它不需要L2/L3模型授权，也不代买家确认或付款。买家一键确认绑定本人、订单、金额、政策/价格/资源版本、摘要与有效期，条件变化必须重算重确认；手动刷新只改变通知方式，余额预留、案/单权限和服务端回执恢复不能后置。渠道尚无补差执行能力时保留待执行及原因，不拿本地记账冒充到账，也不宣称该执行链已验收完成。

三层执行口径必须一并实现：A决定预告和生效版本，关闭A即暂停新的自助规则发布，仍履行已排期/生效规则；B本人领取时短事务签发服务端quoteId与额度预留，不占库存；成单前比较有效保护整篮价和当前同条件整篮价，取较低整套并重分摊，由本人重确认；C从官方确认实付起比较，不重写原订单金额。B/C各自可关闭新覆盖，但不能取消旧义务。价格、条件、期限或模块代次变化使确认失效，既有有效保护承诺仍须兑现。

金额和并发规则在本文固定：金额用整数分，稳定行/件ID分配余分；B签发预留最坏额外让利并限制单笔/活动总额，C成单前预留已承诺最高补差额。原支付实付F、成功退款R、成功补差C、在途预留U满足R＋C＋U≤F；可退余额为max(0，F−R−C−U)，行/件另受原分摊约束。补差与售后在同一核心事务重验并预留余额，渠道在事务外，未知结果继续占额，按原编号查清后结算一次。预算不足要在本人确认前明示该新单未获覆盖，不先承诺再拒赔。

比较保留原架构的可复算底座：同店同SKU/规格/数量/承诺/购买及配送条件的原始整篮、期内实际可买公开价；单档公开满减可计，个人券、新人/会员专价、限量抢购及运费差首版不计，条件不一致或历史缺口转有理由核对。不能拼各商品不同时点最低价。累计差额来自整篮新低事件，先给原篮各件分配新增目标，再过滤已退件；退件目标不转给留件，剩余商品不重拼满减，后来涨价不追回成功补差。完整算法、政策表和设计样本详见架构4.3–4.5、4.8，不另造第二套金额算法。

依赖：沿U2已完成基线，不提前拉入U3–U7；本阶段新增规则库/调度依赖仍选正式版、按单切片冻结，能沿现有时钟/事务完成的就复用。期限、额度、监测频率、B领取策略与标签口径在本人发布政策前显式配置，本文不编经营参数或收益数字。

### 阶段5：花钱先刹车，超限暂停，大额先放待买清单

依赖：沿U2，复用阶段2本人身份/确认/回执、阶段4价格与补差事实及原交易核心，先交确定性规则和可见入口，不依赖AI成功、HSP、SSE或后续升级组。停用增强模块不撤已启用的核心校验；阶段18的R3 L2/L3必须接入本阶段预算与冷静期约束，每一步重验，授权预算再大也不能突破买家本人现行月度预算、单笔限额或已生效冷静期，付款仍由本人确认。

完成条件与验证：本人能设置、看懂超限暂停、把大额购买放入待买清单，冷静到期后重新核价确认，看到有依据的“先别买”建议和不催单的提醒；关闭或宽松设置不强加花费偏好。服务端测并发拆单和多入口合计、单笔限额、重复/未知付款与占额恢复、跨月和退款口径、换号权限，以及直接请求、改规则、取消重建、换入口或重启均不能绕过冷静期；在阶段18再验证L2/L3自动补货、调度重试和恢复不能突破预算或冷静期。设备只走真实用户能点的设置预算、下单被暂停、查看/取消待买项、到期后本人确认及提醒入口，不造调时钟、超预算自动执行或绕过冷静期的隐藏路径。

### 阶段6：双方能举证，处理有理由，不服能申诉

对谁有用：买家 / 商家；承诺争议有可追溯的处理和申诉入口，双方都能说明事实并查看理由。

用户可见：阶段2选中的不符承诺直接带入案件，双方提交证据，商家给出处理理由；不服可申诉，平台处理员只处理分配给自己的案件并本人确认最终结论。先交人工能用的完整流程，AI分诊和原文/缺口/建议/最终稿并排的协作案桌在阶段16增强，不把等待AI作为受理前提。
