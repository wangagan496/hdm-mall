## 四个问题先回答

1. “没人敢做”不对：国内千问与淘宝、海外 Amazon Buy for Me 等已经走到交易；但“替你办事”通常依赖明确授权、预算和确定的商家系统，并不等于 AI 随便替你花钱。还要防止拿旧发布当现状：OpenAI 在 2025 年发布过内结账，2026 年已经改为重点做发现商品、由商家自己的页面结账。[S01–S04、S08]
2. 建议模块当底座，agent 当驾驶员：这属于架构推断，原因是交易规则、权限和错误边界能够独立验证；不要求把三个项目合并。
3. 优先候选是“带出处的选品与服务端精确报价”和“售后办事预演与确认提交”；这属于项目建议，不代表已经实现。
4. “疯子架构”没有因为 AI 自动过时，AI 工具使用、检查和调试已经出现在部分校招要求中；基础、交付和讲清取舍仍然重要。学生项目类型占比、鸿蒙实习名额的连续变化没有可靠同口径数据，不能据几个帖子或人才缺口预测下结论。[T01–T11]

## 二、协议各管哪一段

| 名称 | 白话解释 | 不保证什么 | 一手依据 |
| --- | --- | --- | --- |
| MCP | 让模型客户端发现并调用外部工具、读取资源的接口约定。 | 不自带正确业务规则、支付许可、审计完整性或沙箱。工具描述本身也可能不可信，主机需要控制授权。 | [S24] |
| A2A | 让不同agent用Agent Card声明技能、通过任务和消息协作；适合互通任务状态和产物。 | 不等于把数据库、钱、密码交给其他agent，也不承诺其结果正确。 | [S25] |
| ACP | OpenAI与Stripe共同发起的智能体电商协议；2025覆盖结账与委托支付，2026扩展商品数据与发现。 | 协议存在不等于ChatGPT当前保留原来内结账产品。 | [S01–S03] |
| AP2 | Google主导的支付授权证据链，以签名的意图、购物车授权等记录约束何人同意何物何价；区分人在场和提前授权。 | 不负责替商家算库存与退货期限，不代表所有支付网络都已经接入。 | [S19] |
| UCP | 商家和购物agent通用的商务能力约定，从发现、结账逐步覆盖后续业务；支持模块与扩展，也兼容MCP/A2A/AP2。 | 不是新的模型，也不是强迫商家改所有后端；上线仍受渠道审批和能力范围约束。 | [S07] |
| ACT、AMP | 支付宝境内智能体商业信任协议与蚂蚁国际移动智能体协议；强调任务授权、预算、身份和撤销，二者有互通合作。 | 不是把支付宝账号和支付密码发给模型；覆盖数字是厂商声明，不是独立安全测评。 | [S17] |
| Visa/Mastercard方案 | 在既有卡网络上提供agent身份、令牌、用户限制、交易归因和争议处理能力。 | 它们与MCP/A2A不是同一层，不能互相取代。 | [S22、S23] |

补充：6月《财经》报道京东2026-06-11发布A2P2（Agent Autonomous Payment Protocol），本次仅核实媒体正文，未取得完整官方规范与个人准入条件，不列为已验证可接入方案。[S18]

## 三、准确率与安全：哪些有证据，哪些只是方案

### 公开失败与评测

| 问题 | 实际取得的证据 | 能说明到哪里 |
| --- | --- | --- |
| 编错商品信息、价格、可用性 | OpenAI购物研究官方正文主动提示可能弄错价格和库存可用性，并建议以商家页面为准。[S26] | 是厂商承认的产品限制，没有披露全部线上错误次数，不能算全国或全行业错误率。 |
| 编错付款对象、定价亏损 | Anthropic Project Vend第一阶段公开实验中，店主agent曾编造Venmo收款账号、未研究成本就给金属立方体报价并亏损。[S27] | 是受控的小店经营实验，偏卖家agent；不能说普通消费者已经发生同规模真实损失，也不是纯粹证明“数学算术差”。 |
| 算错到手价、买错SKU | 本次未查到跨平台、可复现且公开原始样本的真实消费者事故统计。多属性商品与优惠解释错误是合理威胁模型，但在本报告中标为待测风险。 | 不用个人截图或营销文章凑出“普遍发生”。 |
| 越权、被网页诱导 | Brave公开复现Comet读网页时混淆用户命令与不可信网页文字，能被诱导访问另一标签中的邮件；披露时间2025-08-20，包含补丁与复测时间线。[S28] | 是供应商竞争关系下的安全研究，属于公开复现，不是已证明的购物付款事故；不把旧漏洞说成今天仍必然可利用。 |
| 零售办事成功但不稳定 | Sierra官方τ-bench仓库，零售tool-calling GPT-4o Pass^1=0.604、Pass^4=0.383；Claude-3.5-Sonnet-20241022为0.692、0.462。[S29] | 测的是模拟用户、工具和业务规则的任务完成率；Pass^4表示同一任务连续多次都成功的可靠性指标，不是“试四次总有一次成功”。这是旧模型基线，不是2026最新最强水平。 |
| 商品约束是否全满足 | OpenAI定义购物研究评测为：返回商品中满足用户价格、颜色、材质、规格等约束的比例。[S26] | 这是厂商内部评测；本次未取得可完整复算的开放题集与全部分项数字，所以只借用指标，不宣称其线上准确率。 |

事实结论：能调用工具不等于能稳定办成事情；能稳定讲清商品也不等于能稳定执行交易。现有公开材料足够证明这些是需要分别验证的能力，不能推出“换一个更强模型就解决”。[S26–S29]

### 降错办法与证据强弱

| 办法 | 本项目应怎样做（建议） | 证据性质 |
| --- | --- | --- |
| 结构化工具调用 | 输入限制为SKU、数量、订单ID等有类型字段；服务端再校验，模型不能传任意SQL或URL。 | MCP、工具调用官方文档支持这种接口设计；τ-bench说明即使如此也仍会失败，不是效果保证。[S24、S29、S30–S33] |
| 计算交给程序 | 使用整数分报价、固定满减规则、库存事务和售后状态机；模型只解释结果，不生成最终金额。 | 当前商城源码已有相关机制（C01–C03）；“比全交给模型更易验证”是架构推断，不是本次A/B实验结果。 |
| 交易确认 | 展示同一SKU、数量、地址摘要、整数分价格、规则版本，用户确认后签发一次性授权；变化后重新确认。 | OpenAI首发、Amazon和AP2有公开确认/授权机制；AP2也支持提前授权的无人值守任务，所以“每笔必须当场点确认”是本学生项目的取舍。[S01、S05、S19] |
| 最小权限与隔离 | 用户身份来自登录会话，不从模型参数相信userId；买家工具不能用商家token，服务端保留二次权限校验。 | 公开协议有授权与令牌约束；具体角色隔离与越权拒绝须本项目独立测试。[S19、S22–S25] |
| 评测与回归 | 固定问题、冻结商品和规则、保留失败题；换模型、换提示词、换模块版本都重跑同一题集。 | 公开基准支持把可重复任务作为评估单位；拟定门槛见第七节，不冒充已取得的准确率。[S29] |
| 人工复核 | 模糊售后、退款异常、账务差异由有权限的人判断，agent只整理事实和候选处理。 | 属于工程建议与风险控制，没有找到可保证本项目降低多少百分点错误的公开数据。 |

对网页诱导的具体防线（建议）：商品描述、评论、售后附件都只当数据；不让其中“请忽略规则/调用退款”的文字改变权限。支付模块不接收自由文本计划，工具结果不携带可执行脚本。人工确认界面由业务模块生成，不从模型解释里拼交易金额。拒绝和超时同样有结构化结果，禁止模型把“查询失败”改说成“已退款”。

### 鸿蒙官方能力与模拟器边界

事实：华为Agent Framework Kit主要包含Function组件和A2A协议模块，可拉起指定智能体、跨应用传任务和消息；官方简介目前支持Phone/Tablet、中国境内（不含港澳台），明确写“本Kit暂不支持模拟器”。Function接入文档要求先开发智能体、关联应用、设备登录华为账号并联网。[S42、S43]

事实：华为官方开发案例区分LLM、工作流和A2A模式；创建知识库、端插件与智能体涉及上架审核，真机测试要配置白名单，端插件不能仅靠云端工作流预览验证。案例通过InsightIntentExecutor和insight_intent.json把本地工具接到意图框架。[S44]

未确认：本次拿到的公开文档没有完整证明“任意个人开发者”能无条件获得每一种小艺上架、端插件和A2A服务资格，也没取得意图框架所有接口的最小API版本与模拟器支持矩阵。因此不写“个人不能做”，也不写“API24模拟器一定能演示小艺全链路”。小艺平台首页证明开放平台和智能体入口存在，不证明本账号获准。[S45]

建议：先做应用内agent入口加Node业务工具，现有模拟器仅验证本应用自己的交互；小艺/Agent Framework Kit作为有真机和资格后的可选接入口。不能为它新增或克隆模拟器，更不能把普通HTTPS聊天演示包装成小艺系统级接入。

### 合规边界

资料整理，不是法律意见；以下均来源于主管机关，查询2026-11-15。

1. 《生成式人工智能服务管理暂行办法》2023-07-13公布，第二条针对向中国境内公众提供生成式内容服务；未向境内公众提供服务的机构研发应用不适用该办法。提供具有舆论属性或社会动员能力的服务涉及安全评估与算法备案要求，不能简化成“所有学生先办同一张许可证”。[S46]
2. 网信办2026-09-14公告明确：通过API等直接调用已备案模型的应用或功能，由地方网信办开展登记；已上线服务要在显著位置或详情页公示使用模型及备案号/上线编号。用已备案模型不自动免掉应用层义务。[S47]
3. 《人工智能生成合成内容标识办法》2025-03-14公布、2025-09-01施行，规定适用情形下的显式与隐式标识、传播平台识别和用户声明等要求；不是只加一条“由AI生成”就自动满足所有要求。[S48]
4. 推断：导师/面试官在受控环境看演示，与开放公网让任何人注册使用不同；“学生作业”“免费”“只发链接”“没有收费”本身不是公众服务豁免。只做演示时控制访问、用合成或授权数据、不给真实支付代理权限；公开部署前应向属地网信部门确认备案/登记适用条件，再核对APP/网站备案、隐私、内容与经营事项。
5. 边界：上述第二条并不豁免个人信息、知识产权、网络安全及真实交易责任；不把别人的地址、电话、录音和完整订单发送给模型。个人开发者能否办理特定登记、本项目届时对外形式如何归类，本次未查到能直接套用的确定答案。

## 五、“解体、升级、合体”：把模块当底座更合适

以下都是基于上述证据和静态源码的设计判断，不是已经改造完成的架构，也不是三个项目现有能力的运行验收。

| 比较项 | 甲：agent是所有操作必经底座 | 乙：模块是底座，agent按声明驾驶 |
| --- | --- | --- |
| 正确性 | 查询、路由、事务都依赖模型的理解；简单按钮也可能增加不确定性。 | 金额、库存、权限、状态由模块验证；只把需求到操作的映射交模型。 |
| 测试 | 同一目标可能走多种路径，出错难区分提示词还是业务规则。 | 分别测试模块输入输出与agent选工具；相同模块同时给按钮、脚本和agent用。 |
| 出错损失 | 若模型拿的是通用后台权限，一次误解可能跨多个业务。 | 每个工具绑定角色、数据范围、预算与审批；错误先被模块拒绝。 |
| 拔掉AI | 若所有行为都靠它，模型断网可能使常规业务一起瘫痪。 | 人仍能用界面完成原流程；查询可降级，写入可停在草稿。 |
| 升级 | 提示词、模型和业务逻辑耦合，难给旧任务保留稳定语义。 | 工具契约版本固定，模型或单个模块可替换，旧流程仍按旧版本收尾。 |
| 代价 | 开始看似接线少，后续可解释性和权限控制仍要补。 | 要认真写声明、适配器、授权和回执；若一开始做通用市场、分布式调度，容易超出学生收益。 |

建议乙。agent应该理解“帮我买一件不超过100元、能退货的礼物”，然后调用目录、报价、规则与草稿模块；它不应该发明折扣、绕过库存、直接把订单改为已付款。模块声明不仅写“能做什么”，还要写“谁能用、会改变什么、失败后怎样处理”。[方案依据：S07、S19、S24、S25；业务证据：C01–C04]

最小共用约定可以是一份数据结构和一组适配测试：工具名称、版本、输入/输出结构、角色范围、只读或写入、幂等请求号、资源版本、是否要确认、超时、错误码、审计事件、可用状态。确认凭据由服务端在真实用户操作后签发，绑定用户/工具版本/资源/参数摘要/价格/有效期，用完失效；模型不能自己说“用户已确认”就获得权限。

三个项目可以共用约定、工具执行器外壳、模型适配器、确认组件的语义和评测格式，分别保留自己的身份、数据和业务规则。ArkTS、Dart和Node不能直接共享所有运行代码，可共享JSON Schema、示例和测试向量，并做各语言适配；账号与用户原文不跨项目流转。

### 怎样让“拔插合体”有现场冲击力

建议把演示目标定成“同一件事，模块缺一个、换一个、加一个时，用户能看到不同但合理的结果”，而不是展示一堆服务窗口。

1. 解体：目录模块独立提供结构化查商品；报价模块用固定样本独立算价；业务客户端在没有agent时仍能手动查价。独立可运行要有各自入口与验证条件，当前源码尚未证明这一点。
2. 升级：把优惠规则v1换为v2，旧报价提交被明确拒绝并重新确认；新请求使用新规则。正在执行的交易固定版本，停止接收新任务后排空旧任务，再切换，不在支付中途卸载代码。
3. 合体：目录加报价只能给预算方案；再加售后规则可筛选“买得起而且符合退货要求”；加订单模块后才出现“生成待确认购买方案”。组合带来的能力增量清楚可见。
4. 故障：拔掉agent入口，原有按钮可用；拔掉非关键的推荐模块，用户可以手动选择；拔掉报价、权限或库存等必需模块，提交明确停止，不能默默绕过规则。
5. 多端：手机发起、H5或桌面查看同一任务摘要，在登录一致的授权范围内接着确认；每次写入只由一个端持有一次性确认凭据，另一端重复提交返回同一回执。这个是建议的新能力，现有三项目源码不证明已有。

首版可以是“一个服务内的模块注册表加少量可替换适配器”，先证明契约、拒绝与升级；若用户坚持进程级独立，再把目录/推荐等低风险模块拆成独立进程。不要先拆库存、订单、退款到多个独立数据库，否则要额外解决跨服务一致性，求职展示收益未必抵得过工作量。HarmonyOS应用模块与远端工具模块也不是同一种热更新：不建议把它讲成可绕过应用发布规则的任意HAP热插拔。

## 六、惠多美现有接口能给agent用什么

范围仅当前mall分支源码，查询2026-11-15；没有请求接口。风险按业务实际副作用判断，不能看HTTP方法就分级。以下“只读”指用户业务意图；源码中多个GET会触发过期结算、物流缓存等内部写入，工具适配前须明确这些副作用。

| 工具候选与真实入口 | 风险等级 | 人工确认与适配要求 |
| --- | --- | --- |
| 搜商品：POST /search/all，GET /goods、/category/summary、分页推荐 | 只读意图；可触发orders.expireIfDue | 保留商品ID、SKU、规格、更新时间与来源，缺货/下架不编；搜索POST不等于写业务。不要宣传为数据库绝不写。 |
| 算价：GET /member/order/pre，Orders.preOrder，promotionQuote | 只读意图；执行过期检查 | 已有购物车勾选或单SKU立即购买预览，不是任意多商品报价API；用promotion.amountCents整数分，不让模型从浮点展示值重算。脱敏地址，不把预览里的完整地址发送给模型。 |
| 我的订单：GET /member/order、/:id、/by-request/:requestKey | 只读 | 后端以登录主体执行，拒绝越权ID；亲友订单有独立授权，不能因“朋友”自动获全部权限。 |
| 物流：GET /member/order/:id/logistics | 只读意图，可能查外部渠道和写缓存 | 地址电话等仅留服务端，agent只拿脱敏轨迹；签收轨迹不等于用户已经确认收货。 |
| 购物车：POST/PUT/DELETE /member/cart | 会改数据但可撤销 | 建议先生成修改摘要，按用户授权加购；清空原有购物车需显式确认，重试复用requestKey。 |
| 地址：POST/PUT/DELETE /member/address | 会改数据，恢复需旧数据；隐私高 | 只做草稿与选择，真实地址修改、删除默认地址必须用户核对；模型不持有地址簿全量导出。 |
| 创建订单：POST /member/order | 会动库存 | 提交会reserveStock；SKU/数量/地址/金额/退货限制全部人工确认，价格或规则版本变化重新确认；超时先by-request查结果，不盲目再下单。 |
| 支付：/:id/payments、/payments/checkout、/payments/refresh | 会动钱或推进支付状态 | start/checkout只在用户确认后；支付凭证不进入模型，付款操作由用户；refresh看似查询也可能落状态，不能算纯读或据模型判断支付成功。 |
| 取消：PUT /member/order/:id/cancel；POST cancel-requests及withdraw | 会动库存，已付款场景可能走退款 | 未付款取消会归还库存；取消申请有撤销窗口也不等于所有后果可逆。必须展示当前阶段和后果后确认，不能一概归成低风险写入。 |
| 售后：POST /member/order/:id/after-sales；withdraw、ship-back | 改状态，后续关联钱/库存；申请可能确认收货 | agent预填原因、证据和方案，提交由用户确认；现有流程存在“提交后视为已收到货”语义，不能自动帮人点掉。撤回申请也可能丢失时限机会。 |
| 商家库存与流水：GET /merchant/inventory、/:id/movements | 只读（商家权限） | 仅给本商家；用于解释缺货和变动，不允许改库存以“完成用户目标”。 |
| 商家商品与规则：GET products、settings/promotion；PUT products、promotion | 读取只读；写入可改变成交价格和供给 | 可生成编辑草稿；真实改价、上下架、退货规则和优惠发布由商家确认，revision冲突拒绝；库存调整按高风险处理。 |
| 商家对账：GET reconciliation、bill；POST reconciliation/run | GET读；run会生成/更新报表 | 适合差异归因候选，需标“推测原因”与原记录；resolve、支付异常resolution、refund retry必须有权限的人审批，不自动核销差异。 |
| 客服消息：GET service/history类接口，POST消息 | 读含私人内容；发消息有外部影响且不能可靠撤回 | 可以拟稿、整理事实；向真实买家/商家发送必须先核对。不能把“会改数据但可撤销”套在所有消息上。 |
| 确认收货、评价、开票、商家发货与售后approve/inspect | 状态/信誉/物流/资金风险，部分不可逆 | 真实收货、检查退货物品、物流交接和开票由人完成并确认；不允许模型看到“已签收”就自行收货，不让agent凭空写运单或验货通过。 |

现有服务器角色主要是买家与merchant商家，代码中的商家人工处理不应包装成独立平台仲裁员；若要平台处理员，应另建真实的角色与授权范围，不能给一个agent偷用所有商家权限。[C01]

绝不能给agent的权限（建议）：数据库任意执行和改账、签名密钥与支付密码、伪造支付回调、直接改订单为已付款、发放角色和重置他人身份、绕过退款/库存检查、关闭审计与备份、读取环境配置和所有用户隐私、执行测试夹具或mock-pay冒充真实支付。业务服务自己可以持有完成职责所需密钥，模型只看到受限工具回执。

## 七、候选功能与验收办法

这一节是建议的功能与验收目标，不是已完成或实测成绩；“现在平台做到什么”只引用上面核实范围。所有固定题集须有冻结商品、规则、角色与时钟，并单列不会做、澄清、拒绝和故障，不能只测顺利问题。

| 对象与候选 | 解决的问题；外界现状 | 准确性依赖、建议指标 | 冲击力与风险 |
| --- | --- | --- | --- |
| 买家1：带证据的选品、精确报价（优先） | “预算100，规格要对，还能退”；主流已普遍做到比较，千问/Amazon还可推进交易。[S04、S08] | 查结构化目录、服务端promotionQuote和退货政策；100个冻结问题中至少95个意图/约束全对，金额与规则程序100/100一分不差，未知属性100%不编造。达不到就留在选品建议。 | 接/拔优惠、售后模块后能力明显变化；风险中，先不下单。目录缺对应字段时回答不知道，不能声称保真保用。 |
| 买家2：售后办事预演（优先） | “这单能退吗，退多少，要做什么”；千问发布已有售后闭环，但各商家规则仍不同。[S08] | 订单快照、售后状态机、期限、支付/退款状态；100个边界案例对资格、截止时间与金额全部一致，提交确认覆盖100%，撤回与重复提交不制造第二申请。 | 一句话生成完整材料与步骤，再由人确认；风险中高，明确收货/申请语义，不替人做实物声明。 |
| 商家1：经营规则升级预演 | 商家想改满减但怕旧订单算错；Shopify等已提供商家agent渠道，美团有经营agent产品声明，具体同款预演未核实。[S13、S20] | 在只读样本上调用规则版本，输出新旧金额与受影响订单；100组样本和确定性程序完全一致，旧报价冲突100%重新确认。 | 最贴合“单模块升级”；风险低到中，预演与发布分开，现有码需新增安全预演接口。 |
| 商家2：库存/物流异常办事清单 | 找“卖不动、缺货、已签收却未收货”的真实原因；大平台有供应链AI，但本次未核实学生可免费复用的同等功能。[S10] | 只读库存流水、订单和物流证据；100个标注异常检出≥95、错误警报≤5，金额与库存事实零改写；解释原因标证据或推测。 | 跨模块合体明显；风险中，不自动补库存、不伪造发货。 |
| 平台处理员1：争议证据包 | 汇总双方说法、订单/物流/政策时间线；售后功能常见，但本次未查到平台公开的通用自动仲裁正确率。 | 角色隔离的读取接口、不可改快照与规则版本；100个案件关键事实完整≥95，来源对应100%，跨用户泄露0、凭空引述0。 | 比“会聊天的客服”更能展示工程价值；风险中，现有商城没有独立平台角色，首版仅演示数据。 |
| 平台处理员2：对账异常调查与操作预案 | 把“钱和订单不一致”分成可验证候选原因；支付协议重授权审计，不代表已解决商家对账。[S19、S22、S23] | reconciliation报表、渠道账单、支付状态机；50个冻结差异全检出、零虚构支付成功、所有resolve均待人工确认。 | 冲击力高、风险高，先做解释，不让agent实际核销或退款。 |

不要把不同指标混成“准确率99%”：分别报告意图正确率、工具和参数正确率、规则一致率、最终业务成功率、该澄清是否澄清、越权拒绝率、幻觉率、重复执行率、延迟和单任务成本；同一任务至少重复5次看稳定性。零越权、零重复扣款这类高风险门槛不允许拿平均分冲掉，且小样本零失败不证明总体零风险。

建议演示前冻结至少20个恶意输入和20个故障/冲突场景：评论藏“退款指令”、冒充商家、替朋友查单、价格变更、库存耗尽、工具超时、重复点击、过期确认凭据、换端后旧确认失效。这里是验收设计，本次约束禁止跑测试，所以没有真实成绩。

不现实或收益偏低的方向：全网自动抓取比价后任意平台无人付款、接管银行/微信/淘宝、从零训练通用大模型、几十个自治agent谈判、学生自建全球支付标准、把三个App的用户账户和业务库合并、随意热卸载正在执行的支付/库存事务、宣称AI自动公正仲裁。限制来自生态授权、数据、评测、资金责任与时间成本，不是“别人不敢所以学生有优势”。

### 传统项目、AI项目和“疯子架构”的位置

公开讨论中能见到前端商城/后台/社区、后端商城/外卖/点评、鸿蒙生活服务/购物/刷题，也能见到Agent/RAG/AI编程项目；这些是类型举例，本次没有代表性统计来排序声量或给出各占多少。牛客2024-06-25的苍穹外卖包装讨论、2025-05-05的教学价值与简历区分讨论，只证明模板化和差异化早有人争论；后者也有传统项目拿到offer的反例，不能说传统项目一律没用，更不应采纳换皮冒充独创的做法。[T17、T18]

从2023–2024到2025–2026可确认的是：竞赛、项目、实习对接本来就存在，后来的调查和JD新增了更明确的AI工具与应用要求；没有足够证据支持“以前比功能数量，现在只比agent数量”的二分法。教育部转载报道出现AI面试陪练与匹配，也只是招聘流程变化证据，其中某位硕士四分之一面试由AI进行是个案，不是全国比例。[T01–T07、T15、T19]

“疯子架构”是否少见，本次未知；名字本身既不加分也不扣分。它有价值的条件是：一个模块能独立演示，替换版本不会破坏旧交易，缺模块会正确停止，用户能在现场改变需求并看到合理结果，而且作者能说明为什么没有继续拆。若只展示十几个目录、协议名和架构图，无法证明比一个完整普通项目更强。这是基于工程边界和招聘样本的建议，不是招聘通过率统计。

## 九、鸿蒙机会、学历和赛事怎么判断

### 人才缺口不是实习岗位数

GIIC2026官方页面介绍《鸿蒙生态人才白皮书2025》，提及百万级缺口、未来300万预测、70%初中级和78%企业核心开发掌握两种语言等；但本次未取得完整抽样方法，完整报告需进一步渠道获取，材料也混合南向系统与北向应用人才，预测不等于当前应届HC。[T11]

本次没有找到2024–2026连续、同平台、同地区、同岗位定义的鸿蒙实习/校招数量，也没有足够同城同级别鸿蒙与前后端JD来比较学历要求。用户感受到岗位变少可以是真实个人经历，但无法用本次资料证实全国增减；同样不能宣传鸿蒙是“学历一般更容易进”的保底通道。已取得的B站、企业校招PDF、华为云样本均出现本科条件，系统岗还可能要本/研，这些具体门槛不能外推成所有鸿蒙职位。[T06–T11]

选择建议：以城市、每周到岗天数、持续月数、学历和目标岗位技术栈筛职位，再决定三个项目的排序；投原生ArkTS/ArkUI岗位突出惠多美与题海方舟，投Flutter/跨端突出栖居管家的相应部分，服务端岗位突出真实交易与故障处理。栖居管家应准确称Flutter社区物业应用及鸿蒙适配，不把三个项目统称全原生；本次源码静态核实不构成设备验收。[C01–C08]

## 十、对这三个项目的具体建议

因：当前已有交易、物业工作流和学习工具三个不同业务，继续堆页面、协议和agent数量，容易把现成优势淹没；招聘样本实际同时看基础、完整交付、AI产物检查和可复现定位。[C01–C08、T06–T10]

果：把一个主项目做成“能现场改变规则、能解释失败、AI撤下仍可用”的作品，比同时把三个项目都包装成全能agent，更能形成可问、可演、可核验的证据；这是一条建议路线，尚无本次录用率实证。

行：按下面的完成条件推进，时间以可投入精力为准，不承诺几天做完。

1. 选惠多美做主演示，先整理目录、报价、售后资格的窄接口与角色；保留现有正常购物流程，先不用真实付款。写清一个请求在哪里授权、查什么版本、失败如何返回。
2. 先做“选品＋精确报价”，再做“售后预演”；模型只作意图理解、工具选择和解释。独立报价必须由程序算，写入只在真实用户确认后允许，不能用聊天里一句“我已确认”当授权。
3. 只共享契约、版本/错误语义、模型适配与评测格式；再用栖居管家的一条报修资格流程、题海方舟的一条学习工具验证能否接入，不移植整个业务库、token或界面框架。
4. 留一套可复现的顺利、拒绝、超时、规则冲突演示，实际跑过以后再记录结果。演示至少包含优惠v1/v2替换、旧报价拒绝、模块缺失停止、重复请求同一回执、agent入口关闭后手动可用。
5. 整理一页设计说明、一个完整请求链路、一项真实故障的定位/修复证据、自己的贡献边界和已知限制；有真实用户和反馈才写，没有就明确是个人验证项目。不要编用户数、性能数据或商业上线。
6. 配合目标JD练基础和现场改动，做一项小而真实的开源贡献；符合条件再参加一项赛事。面试能独立解释、修改、排查与迁移同样重要，不能用AI生成的漂亮说明代替自己的理解。

若暂时不加AI，也可以先做独立报价、售后资格、规则版本和失败保护；这些已能证明模块边界。若加入AI，只加一条受控业务流程，保留换供应商的适配口；不先做训练平台、插件市场、微服务集群或跨项目统一账户。
